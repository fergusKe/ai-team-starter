# 這套閘門為什麼長這樣

**想「改進」閘門之前先讀這一份。**

下面每一條都有人提過、被評估過、被拒絕過。沒有這份紀錄的話，
六個月後有人（或某個 agent）會很合理地把它們一條一條加回來 ——
而那些看起來像改進的東西，有幾條實際上會讓保護變弱。

這套東西經過四輪對抗審查加兩輪第三方確認。過程中兩個審查者
**各自推翻了自己或對方的提案**，所以下面標「拒絕」的，多半不是沒想到，
是想過而且試過。

---

## 用分支前綴封閉列舉，不用路徑白名單

**拒絕的替代**：用路徑判斷「什麼是產品程式碼」，例如
`^(src|app|components|lib|hooks|pages)/`。

**為什麼**：allow-list 沒列到的路徑是 **fail-OPEN**。實測過 ——
一個「只有 `src/a.ts`、完全沒有任何 openspec 檔案」的 PR
會被判定成「✓ 實作階段」直接通過；把程式碼放進 `scripts/`、`types/`、
`server/`、根目錄 config 也一樣逃逸。

封閉列舉漏掉的方向相反：沒列到的前綴一律紅，是 **fail-CLOSED**。

現在只剩兩個 deny-list（`openspec/`、`.github/`），而 deny-list 漏掉
一個路徑代表**多擋**，不是逃逸。

---

## 每個 PR 不需要走兩輪 review

**拒絕的替代**：取消 `chore/` 通道，要求**每一個** PR（包含改一行 README）
都先開一個 spec PR、等人批准合併，才能開實作 PR。

**為什麼**：那個檢查驗的是**存在**，不是**對應**。

一旦 main 上有任何一個 active change（第一週就會有），想跳過規格的做法是：
開 `feat/<某個既有 id>`，然後在裡面寫完全不相干的程式碼。全部檢查都會綠。
所以「每個 PR 兩輪」買到的保證，在第一個 change 合併之後就退化成
「repo 裡至少有一個 active change」—— 不值得每次改 README 都付兩輪 review。

**真正能綁「對應」的是 Scenario ID ↔ 測試的 bijection**，那是另一件事。

代價要說清楚：`chore/` 是一條**靠人**的通道。機器只保證它小到讀得完，
保證不了它不是功能。所以 `AGENTS.md` 規定 chore PR **一律深讀、不抽查** ——
跳過規格的代價就是有人要把每一行讀過。

---

## `chore/` 只有三條機器規則，不是六條

**拒絕的替代**：檔案數上界、行數上界、bytes 上界、單行長度上界、
拒絕 binary、拒絕 symlink/submodule/LFS —— 六條分開寫。

**為什麼**：一個 **bytes 上界**同時涵蓋行數、單行長度、base64 與
minified（一行幾 MB 的 JS 在行數上是 1，在 bytes 上不是）。
`git diff --raw` 的 mode 欄一次擋掉 symlink（120000）與 submodule（160000）。
`numstat` 的 `-\t-` 擋 binary。

六條裡有四條是多餘的，而多餘的規則要人維護 —— 那正是
`AGENTS.md`〈新增流程閘門的門檻〉要避免的免疫系統肥大。

**但 lockfile 不能完全豁免。** 它不列入人類可讀行數（機器產生的，
沒有人會讀，算進去的話任何套件更新都會被擋），但另有一個 bytes 上界：
完全豁免的話，在 lockfile 尾端塞幾 MB 合法 JSON 空白就能把
「review 面積有上界」整個破掉 —— `numstat` 當它是文字、raw mode 是普通
100644、`lockfile-lint` 只驗來源不驗大小、`npm ci` 也接受。

---

## `git diff` 一定要帶 `--no-renames`

**這不是風格，是一個實測重現過的繞法。**

```bash
git mv openspec/changes/<id>/specs/x/spec.md src/interpolation.ts
git diff --name-only origin/main...HEAD
→ src/interpolation.ts          已批准的規格消失了，閘門看不到
```

git 預設做 rename 偵測，而 `--name-only` 對 rename **只顯示新路徑**。
加上 `--no-renames` 之後同一個操作顯示成 D + A，舊路徑重新出現，
每一條規則就都抓得到。

同理路徑要用 `-z` 取 —— git 對含空白或控制字元的路徑會加引號跳脫，
那會讓 grep 比對到錯的路徑。含換行的檔名直接擋（fail-closed，不猜）。

---

## archive 要比對內容，不能只看 status letter

**拒絕的替代**：確認原目錄的每一筆變更都是 `D`（刪除）就好。

**為什麼**：「原目錄被刪了」不等於「archive 裡是同一份東西」。可行的繞法：
複製到 `changes/archive/<date>-<id>/` → 改掉複製過去的 proposal 或 spec
（只要還能通過 validate）→ 刪掉原目錄。git 會看成 D + A，
原目錄的 pathspec 輸出全是 D，那條檢查就過了。

所以改成逐檔比對 blob SHA。但光是比對還不夠，目的地的**綁定**要精確，
不然還有三個假通過的方向：

| 沒做的話 | 後果 |
|---|---|
| 目錄名寫成 `[^/]*<id>/` | id `demo` 配到 `2026-01-01-my-demo/`、`auth` 配到 `...-unauth/`。一個排序在後、內容乾淨的誘餌目錄會**覆蓋掉真正被竄改的那一份** |
| 只檢查「每個來源檔案都找得到」 | archive 裡**多出來**的檔案不會被拒絕 |
| 不檢查 base 上這個 change 存在 | 來源是空集合，每一條都真空成立 |

所以是四件事一起：日期前綴錨定 `[0-9]{4}-[0-9]{2}-[0-9]{2}-<id>/`、
目的地**恰好一個**、來源與目的地的檔案集合**完全相等**、
以及不得順手動到別的 change 的 archive。

---

## Scenario ID 從第一份規格就強制，不等有測試才補

**拒絕的替代**：先只寫進 `openspec/config.yaml` 的 guidance，
等有測試套件、要做 ID ↔ 測試對應的時候再補 checker。

**為什麼**：ID 是**寫進 main 就不能改的鍵**。等到有測試才補 checker，
那時要做 migration —— 比一開始就擋貴得多。而且 guidance 是餵給 agent 的
文字，不是機器在驗；**寫在 config.yaml 就當作交付了，那正是這整套東西
要防的那件事**（這個錯在開發過程中真的犯過一次，由審查者抓出來）。

---

## 視覺證據放 PR 模板，不做成 CI 閘門

**拒絕的替代**：CI 檢查「有可見變化的 PR 必須附截圖 URL」。

**為什麼**：機器只驗得出「有附一張圖」，驗不出「畫面對不對」。
做成閘門會訓練出「隨便附一張圖」的習慣，而那比沒有更糟 ——
它製造「有在檢查」的錯覺。

截圖對 UI 專案是最有價值的 review 材料，**正因為如此它該是 reviewer
要求的東西，不是 CI 要求的東西**。

---

## 測試名稱用中文是 lint 規則，不是閘門

同上：那是風格，不是安全性質。跟 `no-only-tests` 一起放 eslint。

（動機仍然成立：`AGENTS.md` 把「深讀測試的 diff」列為人類的主要工作，
而英文寫的測試名稱掃過去讀不出它在測什麼。）

---

## `check-ruleset.sh` 不接進 CI

**為什麼**：讀 ruleset 需要 `administration: read`，而預設的 `GITHUB_TOKEN`
沒有這個權限。為了一個查詢去擴大 CI 的權限面不划算，而且 fork 的 PR 會直接失敗。

它是給人跟 agent **手動**跑的。它的價值不在建立設定，在偵測漂移 ——
這個模板的前身發生過：`AGENTS.md` 寫著「CODEOWNERS review 擋得住東西」，
而實際設定是 `require_code_owner_review: false`，那幾行 CODEOWNERS
完全沒有效力，**沒有任何東西會告訴你這件事**。

## 不提供 `skip_specs` 之類的流程豁免

**拒絕的替代**：讓「純工具、純文件」的 change 標一個旗標跳過規格檢查。

**為什麼**：旗標一旦存在，判斷「這算不算純工具變更」就回到了語意判斷，
而那正是路徑白名單失敗的同一個問題。`chore/` 分類做的是同一件事，
但它的上界是**大小**（不看內容性質），而且不得碰 `openspec/` 與 `.github/`。

**這條政策原本沒有機器在執行（2026-09-07 外部審查實測，同日堵掉）。**

洞是這樣的：OpenSpec CLI 自己收 `skip_specs` —— `skip_specs: true` ＋ 只有
proposal、沒有任何 Requirement／Scenario 的 change，`openspec validate --strict`
回 valid rc=0；而 `check-pr-branch.sh` 的 Scenario ID 檢查在 specs/ 不存在時直接
放行，註解還寫著「交給 validate 管」。**兩層各自以為對方在管。**

後果是具體的：那份 proposal 合併進 main 之後就滿足了 `feat/` 的「規格已在 main 上」
存在檢查，讓沒有規格的東西走進**沒有 bytes 上界**的實作通道 ——
「無規格變更只走有大小上界的通道」這項機器保證整個失效。

**堵法**：`spec/` 加三條政策檢查。兩個設計決定值得記：

**一、邊界是「問 OpenSpec 自己」，不是「我們也判一次有沒有規格」。**

閘門**不再自己判**「`specs/` 在不在、裡面有沒有 `#### Scenario:`」，
改成讀 `openspec status --change <id> --json`，要求 `specs` artifact 的
status 是 `done`。1.11.0 的型別明列**四個**值：

| 值 | 意思 |
|---|---|
| `done` | **output glob 找到檔案** —— 注意這**不等於「規格有效」** |
| `ready` | 還沒寫（沒有 specs/，也沒設旗標） |
| `skipped` | 被旗標豁免，或檔案放在 discovery 看不到的位置 |
| `blocked` | 依賴的 artifact 還沒完成（例如連 proposal 都沒有） |

`done` 的精確語意值得記一次：它只說「glob 找到輸出」。實測放一個
`specs/demo/notes.md`（完全不是 delta spec）也會是 `done`。
**內容有效性是後面 `openspec validate --strict` 在判的**，這兩關各管一半，
不要把 `done` 讀成「規格寫好了」。

**為什麼改**：第一版自己判，被打出一條**完整的安全繞過**（外部審查實測）：

```
.openspec.yaml         {"schema":"spec-driven","skip\u005fspecs":true}
specs/.hidden/spec.md  一條格式完全正確的 Scenario
```

OpenSpec 的 discovery **忽略 dot-directory**，所以它認為沒有 spec、於是接受
`skip_specs`；而我們的 `rglob("*.md")` **把 dot-directory 算進來**，所以
「`specs/` 有 Scenario」也成立。兩邊對「存在規格」的定義漂掉，整支閘門回 rc=0。

**這正是〈同一件事寫在兩個地方一定會漂〉—— 我在閘門裡重新實作了一次
OpenSpec 的 discovery，而且實作錯了。** 解法不是把 discovery 抄得更像
（`.md` 檔名、capability 目錄層數、要不要跳過 dot-file⋯⋯抄得再像，
OpenSpec 改版還是會漂），是**去問它**。

`skip_specs` 那條子字串比對留著，但降級成**早期訊息**，作用是先給出本 repo
的訊息而不是 CLI 那句「set `skip_specs: true`」。它不宣稱涵蓋完整 YAML key
語意 —— 手刻的每一種都是「解析 YAML 的一個子集」，同一天實測連破兩次：
行首 regex 被 flow style 繞過、全文子字串被 Unicode escape 繞過。
漏掉的寫法由 status 檢查接住，那一條沒有解析器可以騙。

**代價**：多一次 `npx openspec status` 呼叫，而且綁死了它的 JSON 形狀。
所以 fail-closed 寫得很死：沒有輸出、JSON 壞掉、找不到 `specs` 那一項、
status 是沒見過的值 —— **一律拒**。OpenSpec 換版改輸出形狀時，閘門會紅，
不會安靜放行。

**二、三條檢查排在 `npx openspec validate` 之前。** 兩個理由：

- CLI 遇到「沒有 delta」時，錯誤訊息會說 **「set `"skip_specs: true"` in the
  change's `.openspec.yaml` instead」** —— 它在推薦這個 repo 明文禁止的東西。
  排在後面的話，使用者先看到的是那句錯誤的建議。
- 更重要的：**放在後面它們永遠跑不到。** 第一版就是放在後面，四條負向測試裡有
  兩條當場紅了 —— 不是因為防禦壞掉，是因為 `validate` 先擋，斷言指不到被測的東西。
  跑不到的防禦沒辦法被測試鎖住，那就是〈一條恆真的測試比沒有測試更糟〉。
  **要嘛可達，要嘛不要留。**

那四條測試用的是 `run_msg`（連**專屬錯誤訊息**一起斷言，不是只看 exit code），
fixture 一律用 **main 上不存在的新 change** —— 用既有的 `demo-change` 會被
「不准刪／改 main 上的 Scenario ID」那條先擋掉，exit=1 是真的但擋它的不是這條。
突變電池 4 個 0 存活（含「把整段移回 validate 之後」那個）。

## bypass 清單預設是空的

**為什麼**：模板不該替採用者決定要不要留後門。

要加的話（一人專案通常會要）：`bypass_actors` 的兩種 actor type 見
`.github/ruleset.json` 的註解。但要知道 **bypass 是整組的** ——
它同時繞過 required status check，也就是 CI 紅的時候一樣按得下合併。
GitHub 的 ruleset 沒辦法只繞過 review 而保留 CI。

**加了誰就要寫進 `AGENTS.md`。** 不寫的話，讀文件的人（和 agent）
會以為「每個 PR 都要第二個人看過」對所有人成立 ——
而對清單上的人那是自願，不是機制。

---

## 「新增閘門要有真實事故」這條規則的正確讀法

`AGENTS.md` 有一條：**新增任何流程 gate，必須先有一次真實事故作為證據。**

它要擋的是**臆測性**的閘門。**可重現的繞法就算事故** ——
把門檻定成「必須先讓已知漏洞真的傷害 main」會產生荒謬的誘因。

判準是：**你能不能在一個測試 repo 裡把繞法跑一次給人看。**
跑得出來就算證據；跑不出來就是臆測。

上面每一條「為什麼」底下的繞法，都是這樣被證明出來的。
`.github/scripts/test-check-pr-branch.sh` 的案例裡，
負向案例就是那些繞法的回歸測試。（**不要在這裡寫數字** ——
數字會漂，而漂掉的文件比沒有文件危險。跑一次就知道有幾個。）

## 不用 LLM 當 PR 審查的閘門

**拒絕的替代**：接一個 LLM（試過 Gemini）自動審每個 PR，判定不通過就擋下。

**為什麼**：

1. **不確定性會把對的判成錯的。** 業界資料很一致：**false positive 是這類工具
   被關掉的第一名原因**。一個會誤擋的閘門，團隊第一次被誤擋就會開始想辦法繞過它，
   而繞過的習慣一旦養成，它擋真問題的時候也會被繞過。
2. **LLM 的判定不能當決定性事實。** 這整套閘門的設計原則是「只看事實、不做判斷」
   —— 分支名、檔案路徑、diff 大小、blob SHA。把一個機率性的判定放進去，
   會讓整條線的可信度掉到那個判定的水準。

**評估過的中間方案**：讓「LLM 必須**被回應**」成為閘門，而不是讓
「LLM 必須**判定通過**」成為閘門 —— 也就是它留的每一則意見都要有人回覆處置。
這個方向是對的，但它需要一個「處置紀錄」的檢查（而且處置者不得是 PR 作者），
在目前的規模是多餘的複雜度。**等 LLM 真的產出過有價值的發現再說。**

**實際發生的事**：接了四輪都沒成功。workflow 是綠的，但三個 API 通道
（reviews / pull comments / issue comments）**全部都是 0 則**。

> **綠而沒有產出，比沒有更糟** —— 它製造「有在審」的錯覺，
> 而那正是這整套設計最想避免的東西。

所以整個拿掉。要重做的話，先確認官方的 `code-review` extension 原樣能貼得出東西，
再換成自己的 rubric，一次只換一個變數。

## Scenario ID 進 main 之後不能改名或刪除

**拒絕的替代**：只驗格式與唯一性就好，ID 要不要改由寫規格的人決定。

**為什麼**：格式與唯一性都對的情況下，一個後續的 spec PR 仍然可以把
`[AUTH-01-S01]` 改成 `[AUTH-01-S09]`。ID 是之後測試要靠它對回規格的鍵，
改掉等於把那條對應關係**悄悄**拆掉 —— 不會有任何東西變紅。

所以 base 上已經有的 ID，head 必須還在。**新增可以，改名與刪除不行。**
真的要淘汰一條 Scenario，用 OpenSpec 的 REMOVED delta，讓它留下痕跡。

原本這一項是排在「第一次修改既有規格的 spec PR 之前」再做的（那時還沒有
任何 ID 可以被改名）。後來提前實作，理由是**那時是最便宜的時刻** ——
零個 ID 存在，檢查一定過，而且之後沒有人需要再想起這件事。

## 測試環境隔離目前只有規範，沒有閘門

**拒絕的替代**（現階段）：CI 掃測試檔，把寫死的非 loopback 位址擋下來。

**為什麼先不做**：

1. **判斷「這個位址是不是共用的」需要知道團隊實際怎麼部署。**
   `https://api.example.com` 可能是共用的 staging，也可能是當次建立的
   ephemeral。機器看不出差別 —— 一做就變成語意判斷，而這套閘門的原則是
   只看事實。
2. **還沒有人踩過。** 依〈新增閘門要有真實事故〉那條，可重現的繞法才算證據，
   而這件事目前連程式碼都還沒有。

**觸發條件（發生了就做）**：第一次有人把一個共用服務的位址寫死進測試檔，
或第一次因為測試連到共用環境而影響到別人。

那時候要做的**不是**掃位址，而是第 3 條硬規則的機械版：
`pretest` 執行一支檢查腳本，實際去問「我現在連的這一份，是不是可拋棄的」——
問法依當時的部署方式決定（例如要求目標回一個只有測試實例才有的標記）。
**檢查「連到的東西是什麼」比檢查「字串長什麼樣」可靠得多。**

代價說清楚：在那之前，這條靠人。而它的失敗模式很安靜 ——
測試會全綠，破壞發生在別人的環境裡。

## 狀態用算的，人只寫算不出來的那幾種

**拒絕的替代**：在 `docs/WBS.md` 開一欄讓人手動維護狀態
（`Done` / `On-going` / `Next-going` / `Delay` / `Debug` …）。

**為什麼不**：那些值**不是同一種東西**，混在一欄裡會讓兩種錯誤同時發生 ——
可以從 git 推導的被手寫（會漂），推導不出來的被假裝可以推導。

| 類 | 誰決定 |
|---|---|
| **事實**（未開始／規格審查中／實作中／已封存） | `progress.sh` 從 OpenSpec 與 git 算 |
| **CI 健康** | CI 算 |
| **意圖**（`Cancelled`／`Pending`／`TBD`／`Alarm`） | 人寫，**必須附理由** |
| **工作類型**（`Regular`） | 人寫 |

三個具體判斷：

- **「下一個要做」刪掉。** 那是優先序意圖，git 證明不了；而 `週` 那一欄
  本身就是排序。**同一件事寫在兩個地方一定會漂。**
- **「正在 debug」改成 CI 健康。** 「CI 紅」算得出來，「有人正在 debug」算不出來。
- **「延期」暫時不用。** 沒有日曆承諾就算不出延期。等到真的有承諾日期再引入 ——
  那時它會變成算得出來的。

## 週次是排程的證據，不是願望

`progress.sh` 只在一個項目**完全沒有週次**（每一列都寫 `—`）時，才把它算成
「做不了」。有週次、但底下某一列被擋住的，只加一行註記，狀態不變。

**拒絕的替代**：任何一列有阻塞就把整個項目標成被擋住。

**為什麼不**：那會把「可以先做一半」藏起來，而那正是最需要被看見的部分。
一個有三列的項目，兩列做得了、只有第三列在等外部的端點 ——
把整個項目標成做不了，等於憑空少掉兩列可以交付的東西，
而且會讓人以為現在無事可做。

## 外部缺口不給週次也不給點數

`docs/WBS.md` 裡代表**外部缺口**的那一組（對方還沒提供的能力、對方明文拒絕的
功能、還沒裁決的產品語意）**刻意留空週次與點數**。它們的週欄只填 `決策≤Wn` ——
那是**決策期限**，不是交付估時。

**拒絕的替代**：跟自己的工作一樣排進 W1–W12。

**為什麼不**：**完成時間不由你控制。** 給它一個週次就是在假裝你排得動它，
而那個假裝會一路傳導到下游 —— 依賴它的功能也會跟著拿到一個假的日期。

還有一件事同樣重要：**分類要夠細**。「對方還沒提供」與「對方明文拒絕」是完全
不同的處境 —— 前者去問就有機會，後者要翻案得先翻產品決策。混成同一個「外部缺」，
會讓人一直重提已經被否決的東西。

阻塞類型的詞彙是從 `docs/WBS.md` 的〈阻塞類型〉表讀的，腳本裡沒有寫死任何一個詞
（見〈詞彙在文件裡，就從文件讀〉）。**這兩種處境要宣告成兩個不同的類型**，
不要共用一個。

## 工作分解表的規則接進 CI，ruleset 的檢查不接

`progress.sh --check` 在 CI 裡；`check-ruleset.sh` 不在。看起來不一致，
但**判準是權限，不是重要性**：

| | 需要什麼 | 在 CI |
|---|---|---|
| `progress.sh --check` | 只讀 repo 裡的檔案 | ✅ |
| `check-ruleset.sh` | `administration:read` | ❌ 為它擴大 CI 的權限面不划算 |

**解析一律 fail-closed。** 看起來像資料、卻解析不了，一律報錯，不准安靜地跳過：
找不到表、表頭畸形、表格被空行截斷、欄數對不上、第一筆漏了 ID、ID 重複、
依賴 ID 打錯或夾了 Markdown。

這一條是被實測逼出來的。在一次真實專案的對抗審查裡：

1. 第一次跑 `--check` 就抓到 **42 條真實違規** —— 文件寫著「每一項缺口都要有
   決策期限與 fallback」，實際上一半以上沒有。**宣言與事實的差距是機器量出來的。**
2. 後來把解析改成「只在工作分解表的範圍內解析」，反而挖出一個更大的洞：
   只要表頭寫成 `| **ID** |`，整張表就被當成別的表略過 ——
   **122 項掉到 19 項，而 `--check` 照樣是綠的。**

所以比對與抽 token 之前一律先正規化（剝 Markdown／HTML、統一連字號）。
**不要拿原始字串去比對** —— 加一個星號就能讓整段檢查失效。

每一條都有負向測試（`.github/scripts/test-progress-check.sh`）。
**一個從來沒紅過的檢查等於沒有檢查** —— 上面每一條都是先實測繞過成功，才補起來的。

**沒有 `docs/WBS.md` 的專案不受影響**，`--check` 直接通過。

## `docs/WBS.md` 算規則面，不算文件面

它在 `governance/` 分支的允許清單裡，跟 `ci.yml`、`AGENTS.md` 並列。

**為什麼**：`progress.sh --check` 從它讀決策期限、fallback 與依賴關係，
所以改它會直接改變閘門的判定。一份「改了會改變閘門結果」的檔案，
就是規則的一部分 —— 讓它能夠夾在功能 PR 裡被改掉，等於讓閘門可以被靜默放寬。

`docs/ROADMAP.md` 一起納入。**理由後來變成同一個**：它現在也是
`--check` 的輸入（裡面的 ID 會被驗），見〈排程只放一份〉。

**代價**：改工作項目要走 `governance/` 分支。這比較麻煩，
但工作分解表本來就不該是隨手改的東西。

## 依賴的服務還沒好，就自己先做一個可拋棄的

**拒絕的替代**：等對方把 API 做出來再開始；或是在元件裡直接寫死假資料。

**為什麼不**：等，會讓功能規劃被對方的進度綁架 —— 而且「對方還沒規劃到」
跟「這件事做不了」被混成同一件事之後，計畫表上會出現一整片假的「做不了」。
寫死假資料則跑不完需要持久化的流程（例如「應徵 → 對方看到 → 婉拒 → 我收到通知」）。

**改成**：自己蓋一個**真的、可拋棄的**後端 —— Route Handlers ＋ 一個丟掉也沒關係
的資料庫。功能先做完，之後再銜接。

三條規則，缺一條這套就會垮：

1. **一份契約，兩個實作。** 用 schema 定義每一個操作的輸入與輸出，
   本地版與真實版都要滿足它。**這是唯一的真實來源。**
2. **資料存取只有一條路。** 元件裡不准出現 `fetch` ——
   散在各處的話，之後銜接是重寫不是切換。
3. **同一組契約測試對兩個實作都跑。** 只跑本地的話，
   這整套會退化成「自己寫給自己看的假後端」。

**唯一的危險是：本地版什麼都做得到，於是會養成對方永遠滿足不了的期待。**
所以本地版要**刻意複製對方的怪癖**（那些「看起來像壞掉、其實是規格」的行為）。
本地版比真實版好用，就是在製造假象。

**銜接要漸進，不能全有全無。** 從早期就定期切到真實版跑一次，
然後逐步把已對齊的操作切過去。留到最後才第一次接，一定會炸。

> 這是 L3 講義那兩個東西的組合：**MockDB**（模擬外部系統的回應格式，
> 不需要真資料庫）與 **TestDB**（自己系統專用、動了也沒關係的資料庫）。
> 依賴的那個服務就是那個外部系統。

## 狀態只算一次，別的工具跟它要

**拒絕的替代**：每個消費端各自解析工作分解表、各自算狀態，
並在文件裡提醒「這幾個地方要同步」。

**為什麼不**：實測過。在一個真實專案裡，指令、網頁、Excel 匯出三個地方
各自實作了同一套判定，**同一份來源給出三個不同的答案** ——
等外部 19 / 9、已取消 6 / 8。原因是各自對兩件小事做了不同假設：
標記要不要看續行、阻塞欄要不要看原文。

而且那個同步點**是我們自己在註解裡警告過的**。警告了，一小時內還是咬了。

**改成**：`progress.sh --json` 吐出解析結果與算好的狀態，
別的工具吃它，自己不解析也不重算。

> **同一件事寫在兩個地方一定會漂。**
> 解法不是「寫個文件提醒兩邊要同步」，是**讓它只有一份**。

**代價**：消費端多一次 subprocess 呼叫，而且綁死了輸出格式。
換來的是不會再有兩個數字。

## 排程只放一份，過期的那份用刪的，不是加警告

一份「產品全貌」文件很容易長出自己的週次表。工作分解表重排之後它不會跟著改，
於是同一個 W8 在兩份文件裡變成兩件事，而且**沒有任何東西會發現**。

實際踩到的處置是在檔案頂端加警告 banner、內容一個字沒改 —— **那沒有用**。
警告在最上面、過期的表在下面，讀的人滑過警告就看表了。

所以：**週次只放在 `docs/WBS.md`**。`docs/ROADMAP.md` 只寫產品意圖，
並用 ID 指向工作分解表；`progress.sh --check` 連它一起掃，
指到不存在的 ID 就紅。**兩份文件的關係是索引，不是副本。**

拒絕的選項是「把兩份都改成對的」—— 那只是把漂移的時鐘撥回一次。

## 認不得的東西要露出來，不能靜靜消失

網頁的群組是從 `## <ID> 標題` 解析的，而那個 regex 曾經寫死只認兩種前綴。
換一個命名，整組的項目就從畫面上消失，**而計數仍然是對的** ——
兩邊都不會報錯，只是少了一整組。

改成兩件事一起做：前綴不寫死，而且**畫面上多一個「沒有群組標題的項目」區塊** ——
凡是歸不到任何群組的項目一律列在那裡，並印出缺的是哪個標題。

同理，銜接清單是哪一組也改成用算的（被別的項目寫進「阻塞」欄的那些項目所屬的組），
不是寫死組名。**寫死的失敗方式是側欄靜靜地空掉。**

## 引用檢查要連群組 ID 一起驗，而且要挑對文件

原本只驗工作項目 ID（`FE-M09` 這種有數字的）。群組 ID（`FE-O`）沒有數字，
整套檢查看不到它們 —— 重切群組之後 `FE-D`／`FE-I` 這類引用在四個地方躺著，
**其中兩個就在工作分解表自己裡面**，另外兩個在 `AGENTS.md` 與 `CLAUDE.md`
（都是「前端有自己的後端（`FE-D`）」這句）。是人肉盤點才找到的。

群組引用斷掉的後果比項目更糟：讀的人會去翻一組不存在的能力。

**掃哪幾份文件是每個專案自己的選擇**，寫在 `progress.sh` 的 `REF_SOURCES`。
判準是那份文件裡的 ID 是**真的引用**還是**格式範例**：

- 會直接點名「哪一組是本地後端」的 `AGENTS.md` 是真引用 → 加進來
- 判準是**圍籬外**有沒有範例 ID。模板 README 那張示範表在圍籬裡，
  掃它其實是安全的；預設不加是因為**複製模板的專案，它的 README
  寫什麼我們不知道**

**圍籬程式碼區塊一律跳過**（``` 之間）。它同時是「範例」的通用出口 ——
但只在圍籬內，圍籬外的同一個 ID 照樣要紅，否則它會變成萬用消音器。
測試同時盯這兩邊。

`docs/DECISIONS.md` 刻意不驗：它是歷史，會引用當時的 ID 當例子
（「依賴指向不存在的 `BE-G99`」），那正是它該做的事。

## 一條恆真的測試比沒有測試更糟

**拒絕的替代**：測試套件全綠就算數；或是「再多寫幾條測試」。

`--check` 有一條測試專門防「`APP-C01` 被誤判成群組 `APP-C`」。它斷言錯誤訊息裡
**不該**出現「群組 APP-C 不存在」—— 但 fixture 裡就有 `## APP-C 應用`，
`APP-C` 是一個**定義過的**群組，那句話本來就永遠印不出來。
這條斷言恆真。實測把 regex 的 `(?![0-9A-Za-z])` 拿掉、讓誤判真的發生，
四十條照樣全過。

**所以驗收條件不是「測試全綠」，是「壞掉的程式會讓測試變紅」。**
補測試的時候先造一個突變體，看它有沒有被殺死。這一輪殺掉八個：

| 突變 | 補上的測試 |
|---|---|
| 群組 regex 拿掉尾隨的 `(?![0-9A-Za-z])` | 改用**沒有定義過**的群組 `APP-Q` |
| 拿掉「一張群組都認不出來就不驗」的守衛 | 把所有群組標題改掉，應該綠 |
| 拿掉 `APP-O01/02/03` 的尾隨展開 | `APP-C01/99` 應該報 `APP-C99` |
| 左邊界用 `\b` | `依賴APP-D完成`（中文緊接）應該紅 |
| 群組前綴寫死 `{2,4}` | `ADMIN-Z` 應該紅 |
| 抽 ID 之前不過 `plain()` | HTML 註解裡的舊 ID 應該綠、`APP\u2011D` 應該紅 |
| 圍籬不認 `~~~` | `~~~` 裡的範例應該綠 |
| `--json` 的 `violations` 永遠是空的 | 同一筆違規要同時出現在兩邊 |

**代價**：測試檔變長，而且每一條都要寫清楚它在防哪一個具體的壞掉方式。
不寫的話，下一個人會把它當成可以隨手刪的重複。

後面幾輪又補了十四個，總共二十二個，每一個都實測過會不會被殺死。
**存活的突變體才是資訊** —— 全死代表這一輪沒學到東西，
而下面有兩個是審查者先預測會存活、實測也真的存活的：

| 突變 | 補上的測試 |
|---|---|
| 範圍只展開兩端 `range(lo, hi+1)` → `(lo, hi)` | 範圍中間的 ID 不存在要紅 |
| 反向判斷 `lo >= hi` → `lo > hi` | 兩端相同（`APP-C01`–`APP-C01`）也要紅 |
| 項目 regex 尾端加回 lookahead | `APP-C01/02x` 裡的 `APP-C02` 照樣要驗 |
| catch-all 不吃斜線尾巴 | `APP-C01/2` 的 `/2` 要報 |
| 斜線後面的組別字母不比對 | `APP-C01/P02` 要紅 |
| 跨度上限不報、第二端位數不驗 | 各一條 |
| `is_id_row` 改回 `[0-9]+` | WBS 第一欄的 `APP-C1` 也要紅 |
| 阻塞欄規則拿掉 | 阻塞欄指向有工作週次的項目要紅 |

`lo > hi` 存活這件事告訴我們：「反著寫」跟「兩端相同」被同一行程式處理，
但只有前者有測試 —— **一條 `>=` 有兩個意思，測試只驗了一個。**

## 跳過機制要自己會叫

**拒絕的替代**：圍籬跳過就是跳過，解析不出來就當作沒有。

「圍籬裡是範例，不驗」這個規則有一個後門：**一個沒關起來的圍籬會讓
檔案後半段的引用全部消音，而且是綠的**。想關掉整份文件的檢查，
只要在最上面打三個反引號就好。

所以掃完一份檔案，`in_fence` 還是 True 就報違規。同一個道理：
`plain()` 會剝掉反引號與 `~`，拿正規化後的字串去認圍籬，
那一行會變成空字串 —— **結構看原始行，ID 看正規化後的字串**，
兩者不能混。

網頁那邊是同一條原則：銜接清單是哪一組用算的，
算不出來（沒有任何項目填了阻塞欄）就在面板裡**寫出來**，
不要留一個空的清單 —— 標題說有這一組、底下什麼都沒有，
讀的人只會以為是還沒載入。

## 誤報一次，好過漏報六個月

**拒絕的替代**：把 `USB-C3`、`APP-C01-05 點` 這種「剛好長得像 ID」的字排除掉。

引用掃描分不出「這是工作項目 ID」還是「剛好長一樣的別的東西」。
要排除就得列一份例外清單，而**例外清單自己會漂** —— 那正是這套閘門在防的事。

所以方向固定：在 `REF_SOURCES` 那幾份文件裡，`大寫-大寫＋數字` 是保留字，
寧可誤報。漏報的代價是一個懸空 ID 躺六個月沒人發現；誤報的代價是有人
被擋一次，把那段字放進圍籬或改寫。兩者不對稱，所以不對稱地選。

## 接力式的檢查，每一棒都會掉東西

**拒絕的替代**：每發現一個漏掉的寫法就再補一條 regex。

引用掃描曾經是三條 regex 接力 —— 一條抓範圍、一條抓斜線清單、一條
catch-all 報不合法。每一條有自己的邊界，設計上「這一條放掉的交給下一條」。
實測**放掉的東西沒有人接**：

| 寫法 | 為什麼靜默 |
|---|---|
| `APP-C01/02x` | 斜線那條的尾隨 lookahead 在 `x` 上失敗，回溯把 `/02` 整段丟掉；catch-all 從頭吃到 `/` 就停 |
| `APP-A01`–`APP-A99x` | 範圍那條同一個洞，而第二端前面那個 `-` 又被另外兩條的左邊界 `(?<![A-Za-z0-9-])` 擋掉 |

第二個是第一個修好之後才被審查者找出來的 —— **同一個缺陷長在另一條
regex 上**。補第三條、第四條只會再生一個。

所以改成一個 token、一份文法：`plain()` 之後切出最大 token，用三種
合法形狀去 fullmatch，parse 不完整就報。**這裡就是最後一條檢查**，
不再有「交給下一條」。

不變量寫進程式裡，因為它反直覺：**token 吃的字元集合要涵蓋邊界擋的
字元集合。** 不涵蓋的話，回溯會生出一個比較短、邊界剛好成立的假匹配。

第一次只寫了右邊界，然後審查者用 `APP-A01--APP-A99` 打回來：左邊界擋 `-`，
而尾巴只在 `-` 後面接英數時才吃 `-`，於是 `--` 從中間裂開、後半被左邊界
擋掉，**整段靜默**。同一個不變量，另外半邊。左右都要算。

**代價**：散文用的 token 頭部要求至少一個數字，不然 `SETUP-GITHUB.md`、
`X-Ray`、`E-Mail` 全會被 parse 成假違規（實測：README 立刻多一個）。
所以 `DEP-GXX` 這種沒有數字的打錯，在散文裡看不到 —— 只有阻塞欄那種
**受控欄位**用寬 token 才抓得到。文法同一份，差別只在「哪些字拿去
parse」，而那是因為欄位受控、散文不受控。

## 只有 ID 有文法，別的欄位沒有

**拒絕的替代**：週次跟點數是給人看的，不用驗。

第一欄早就在報「不是合法的工作項目 ID」，第四欄與第五欄什麼都沒有。
於是 `W1-W3`（ASCII 連字號，跟正確的 `W1–W3` 差一個鍵）會讓那一項的
排程**靜靜消失**：週次變成「沒有排程」，`--check` 是綠的 ——
連帶「工作不得排在它依賴的裁決之前」那條也因為起始週是 None 而跳過。
**一個打錯的字元把一條閘門關掉了。** `5點` 一樣：那一列的點數直接不算，
總數少掉沒有人會發現。

現在七欄裡只剩「項目」與「工作」是自由文字。

## 認證用的腳本自己會 fail-open

**拒絕的替代**：加一條「`cp` 失敗就 exit 1」的守衛。

`test-progress-check.sh` 用 `git rev-parse --show-toplevel` 定 ROOT，
再把 `progress.sh` 複製到臨時目錄去跑。把這套東西複製出去（新專案還沒
`git init`）就解析失敗 → `cp` 失敗 → 臨時目錄裡留著**上一次執行留下的
progress.sh**，於是測到的是舊檔，而且全綠。實測：放一個 `exit 0` 的
stub 進去，整套照樣全過。

修法不是加守衛，是**刪掉複製那一步** —— 用絕對路徑直接跑那一份。
守衛擋的是一條已知的失敗路徑；拿掉那一步是讓那條路徑不存在。

## 撈不到就當作沒有，是最後一種 fail-open

**拒絕的替代**：受控欄位換一張比較寬的網去撈 ID。

阻塞欄一度用一個比散文寬的 token 去 `finditer`，理由是「欄位是受控的」。
撈不到就當作這一格沒有阻塞 —— 而下面這幾種跟「真的沒有 ID」長得一模一樣：

    DEP-G 待銜接        只寫群組，parse 成功之後直接丟掉
    DEP-G０１ 待銜接      全形數字，token 在它前面收尾
    DEP_G01 待銜接      底線被 plain() 剝掉，變成 DEPG01
    DEP-G01--DEP-G03    雙連字號，後半段消失

而週欄與點欄早就是**整格驗**的。所以阻塞欄也整格驗：把切得到的 token
與阻塞類型的名稱拿掉之後，不准再剩下任何 ASCII 英數。做完之後那張寬的網
就可以刪掉 —— **「同一個東西兩種讀法」的來源跟著消失**。

順帶治好一個更小的病：`scan_ids` 回傳的群組引用在阻塞欄被接住卻不用。
**parse 成功卻不用結果，跟 parse 失敗不報一樣是漏。**

## 訊息用字統一，可能讓測試變恆真

**拒絕的替代**：訊息寫得一致比較好讀，沒有別的影響。

「WBS 第一欄的 ID 不合法」與「引用裡的 ID 不合法」原本用字不同（「工作項目
ID」對「工作項目編號」）。統一成同一句之後讀起來一致多了 ——
但 `docs/WBS.md` 整份都在敘述掃描範圍裡（表格列也是），於是那條測第一欄的
測試，needle 兩條路徑都印得出來。**把第一欄整條放寬，測試照樣全過。**

實測：`is_id_row` 改回 `[0-9]+` 這個突變體在統一用字之前會被殺死，之後存活。

所以 needle 要挑**只有那一條路徑會印的字**（這裡是「會被當成上一列的續行」）。
這一類已經栽過三次：`APP-C01` 被誤判成群組那次、阻塞欄展開那兩條、
還有這一次。三次的形狀都一樣 —— **斷言指向的那句話，不只一條路徑會印。**

## 一條 `>=` 有兩個意思，第二次

ID 範圍補了 `lo >= hi`，並且寫下「`>` 這個突變體會存活」。
週欄的範圍後來也補了同一條規則 —— 然後**只測了反著寫，沒測兩端相同**，
`>` 的突變體又活了一次。

同一個坑第二次踩，所以寫在這裡：**看到 `>=`，就要問「相等那一半有測嗎」。**

## 範例跟資料要用同一把尺

**拒絕的替代**：圍籬只在引用掃描跳過就夠了。

`docs/WBS.md` 被讀兩次：一次解析工作分解表，一次掃描引用。**圍籬只在
第二次有效。** 於是一段 ```` ```markdown ```` 包起來的示範表格會被當成
真的工作項目讀進來 —— ID 註冊、點數計入、狀態算出來，而引用掃描那邊
又跳過它，變成一個「永遠存在、永遠沒人引用」的幽靈項目。

實測（用改動前的腳本）：

    items = ['APP-X99', 'APP-C01']   ← 範例被讀成真項目

**同一份檔案、同一支腳本、同一個跳過機制，兩種讀法。** 這正是這支腳本
整份在抓的病，而它長在最核心的地方，五輪審查都沒看到。

## 受控欄位不能用散文的正規化器

**拒絕的替代**：都是同一份文件，用同一個 `plain()` 就好。

`plain()` 是給散文用的：它會整段刪掉 HTML tag、HTML 註解、Markdown 連結
外殼 —— 對散文是對的（那些不是讀者看到的字），對**受控欄位是災難**。
阻塞欄寫 `<待確認>`、`<!-- DEP-G01 -->`，正規化完是空字串，
跟「這一格真的沒寫東西」完全一樣。

方向剛好相反：散文要「只留讀者看到的字」，受控欄位要「**看不懂的東西
留在原地讓它被報出來**」。所以拆成 `normalize()`（兩邊共用的同形字元
折算）＋ `plain()`（散文）＋ `plain_field()`（受控欄位，只剝強調符號）。
共用的那一段要抽出來，不然同一個字元又會有兩種讀法。

## 詞彙在文件裡，就從文件讀

**拒絕的替代一**：把 `待銜接`／`待裁決` 寫死進腳本。
**拒絕的替代二**：用形狀規則猜（「中文」或「英文-中文」就算類型）。

阻塞欄只准放工作項目 ID 與阻塞類型的名稱。第二種是每個專案自己的詞彙，
所以一度改用「殘留法」：把切得到的 ID 與長得像類型的詞拿掉，剩下的字
如果還有 ASCII 就報。

**那不是「不寫死詞彙」，是寫死了另一件事** —— 詞彙必須長成「純中文」或
「英文-中文」。兩邊都漏：

| 阻塞欄寫 | 殘留法 | 為什麼 |
|---|---|---|
| `今天天氣真好` | 綠 | 純中文永遠不含 ASCII，100% 免疫 |
| `x-待銜接` | 綠 | 形狀對了就過，而形狀沒有語意 |
| `WIP`、`外部 API` | 紅 | 誤報 |

而詞彙**本來就宣告在文件裡**：`docs/WBS.md` 有一張
`| 阻塞類型 | 意思 | 該做什麼 |` 表。從那張表讀第一欄就好 ——
跟群組是從 `## XX-Y 名稱` 標題讀出來的是同一個道理。
模板裡一個詞都不用寫，而「沒宣告過的類型」會紅。

## 同形字元不要用清單

**拒絕的替代**：再補幾個 `.replace()`。

原本是一串手寫的替換，每被審查一次就補幾個（U+2010-2014、FF0D、
2212、2015⋯⋯）。第六輪一口氣又找到六個還在外面的：U+2500 `─`、
U+30FC `ー`、U+FE63 `﹣`、U+2043 `⁃`、U+200E LRM、U+2060 WJ、U+FE0F VS16 ——
每一個都讓 ID 從中間裂開、整段靜默。

**「靠清單」本身就是那一類問題，不是清單不夠長。** 改用 Unicode 類別：
`Cf`/`Mn` 拿掉（不佔位的格式字元與標記），`Pd` 折成 `-`（連字號類），
再明列幾個不在 `Pd` 裡但畫面上一樣的（2212、2500、30FC、FF70、2043）。

**不要用 `NFKC`。** 兩位審查者各給了一半理由：它不會把 en dash／em dash／
U+2212 折成 `-`（現有防禦會全部失效），而且它會把 `①` 折成 `1`（過頭）。

## 左右邊界是兩種東西，不要用同一句話概括

**拒絕的替代**：不變量寫成「token 吃的字元集合要涵蓋邊界擋的，左右都算」。

那句話**對右邊界成立、對左邊界不成立**，而且照著它改實作會壞掉：

- **右邊界是回溯風險。** token 尾巴貪婪吃完之後右邊界必然成立；
  不涵蓋的話，回溯會生出一個比較短、右邊界剛好成立的假匹配。
  實測出過兩次（`APP-C01/02x`、`APP-A01--APP-A99`）。**必須涵蓋。**
- **左邊界不是回溯風險**，是「哪些出現位置要掃」的取捨。`finditer`
  由左往右掃，lookbehind 只決定一個位置可不可以起頭；擋掉頭部吃不到的
  字元不會生出假匹配，只會讓那個位置不被掃。

照「左右都算」去放寬，實測立刻誤報：`CONTEXT.md` 裡的 regex 字面
`[0-9a-zA-Z\-]+` 被讀成「群組 A-Z 不存在」（頭部改成先吃 `[A-Za-z0-9]*`
也一樣，會切出 `zA-Z`）。散文裡本來就有 `a-zA-Z` 這種東西，
而黏在英數後面的 ID 不是真的引用形式 —— 這個取捨往「不掃」的方向站。

**一句漂亮的不變量比一句囉唆的危險。** 修的是陳述，不是實作。

## 斷言要指得到被測的那件事

這一類已經栽第四次，四次的形狀都不同，所以列在一起：

| 次 | 形狀 |
|---|---|
| 1 | needle 指向的那句話**永遠印不出來**（fixture 裡群組是定義過的） |
| 2 | needle 指向的那句話**另一條路徑也會印**（阻塞欄展開靠敘述掃描滿足） |
| 3 | 同上，但成因是我**把兩條訊息的用字統一了**（`is_id_row`） |
| 4 | needle 指向的地方**根本看不到被測的事** —— `--check` 只印違規與摘要，不印項目表，所以「範例被註冊成真項目」在它的輸出上完全看不到（突變體 105/105 全過） |

第 4 種的解法跟第 2、3 種一樣：**改問結構化輸出**。`run_blockers_has`
與 `run_no_item` 都直接讀 `--json`，敘述掃描與摘要都滿足不了它們。

## 一份文件的「哪些行算數」只能有一種答案

**拒絕的替代**：三個迴圈各自寫一次 `if 圍籬: 翻轉`。

`docs/WBS.md` 被讀三次（讀阻塞類型表、解析工作分解表、掃描引用），
三處各寫了一次圍籬判斷 —— 而且三處錯在同一個地方：**翻轉不是 Markdown
的規則**。CommonMark 說閉合圍籬要跟開啟同字元、長度不能比它短。
只數次數的話，這三種寫法都能無聲塞進一個假的工作項目：

    ````markdown        外四個、內三個。內層被當成「關」，表格曝光
    ```markdown / ~~~   不同字元，照樣被當成關
    <!-- 跨行註解 -->    `plain()` 的註解正則是逐行的，WBS 解析根本沒看

三個都是 `--check` rc=0、`--json` 裡真的多一個項目。而且切換次數是偶數，
**連「未閉合圍籬」那條也不會響**。

所以收成一個 `visible_lines(text, src)`：CommonMark 的閉合規則、跨行註解、
未閉合的圍籬與註解都報，三個迴圈都吃它。
**「哪些行算數」是一個判斷，不是三個。**

## 查表排在文法前面，表就成了後門

阻塞欄的判斷順序是「先看是不是宣告過的類型，再看是不是合法 ID」。
於是**表裡放什麼，阻塞欄就放行什麼**：宣告一個 `DEP-G01`，
某一項真的被它擋住時，那條相依性從 `blockers` 靜靜消失（rc=0）；
宣告一個 `DEP-G`，「群組不是阻塞」那條也被繞過。

修法不是調換順序（那會讓類型永遠被 ID 文法搶走），是**讀表的時候就擋**：
類型詞跟 ID 文法撞名、或含有分隔符，在讀表那一刻就報。
**能在源頭擋掉的，不要留到使用的地方才判斷。**

順帶：表頭的定義是「下一行是分隔線」，不是「第一欄剛好寫著阻塞類型」——
不然任何一張表裡出現一列 `| 阻塞類型 | … |`，底下每一列都變成合法宣告。
這跟工作分解表的表頭判斷是同一條規則，早就寫過一次，這裡漏了。

## 正規化有一條線：折到「看不出差別」為止，不能再往前

**拒絕的替代**：`Cf` 能整類拿掉，`Mn`／`Pd` 應該也可以。

- `Cf`（格式字元）**可以整類拿掉** —— 零寬、LRM、軟連字號，
  拿掉之後畫面完全一樣。
- `Mn` **不行。** 為了 VS16 而整類剝過，但 `Mn` 裡有越南文聲調、
  泰文母音符號 —— 剝掉之後 `ป่า` 與 `ปา` 撞成同一個字串。
  改成只剝變體選擇符。
- `Pd`（連字號類）**不行。** 裡面有 U+301C 波浪號與 U+30A0 片假名雙連字號，
  它們畫面上不像 `-`，而 `〜` 在中文裡是「到」。整類折的話
  `APP-A01〜APP-A03` 會被當成範圍靜靜展開 —— 而同一支腳本的週欄
  只認 `–`，訊息還特別寫「是 – 不是 -」。**同一支腳本兩種範圍文法。**

線在哪：**折到「畫面上看不出差別」為止。** 再往前一步，
就從「把同一個東西讀成同一個」變成「把不同的東西讀成一樣」——
那是這份文件從頭到尾在防的漂，只是換了個方向。

波浪號不折之後會被讀成兩個獨立引用、中間完全不驗，所以另外補一條：
**看起來像範圍就當範圍檢查**，符號寫錯要說出來。

## 一條叫人做無用功的訊息，比沒有訊息更糟

欄數對不上時的訊息是「敘述裡的 `|` 要寫成 `\|`」。而切欄的程式是
`line.split("|")`，**完全不理跳脫字元** —— 照著做，還是報同一條。

沒有訊息的話，人會自己去看程式；有一條錯的訊息，人會照做、失敗、
然後懷疑自己。**訊息是介面的一部分，它說的話要是真的。**

## 斷言指不到被測的事：第五種形狀

前四種在上面那張表。第五種：**退出碼與訊息都看不到差別。**

「`\|` 有沒有被還原成真正的 `|`」——欄數切對了就 rc=0、也沒有錯誤訊息，
格子裡存的是 `\|` 還是 `|` 從外面完全看不出來。突變體因此存活。

解法跟第二到第四種一樣：**改問結構化輸出**。`run_field_has` 直接讀
`--json` 裡那個欄位的值。到目前為止三個 helper 都是這樣來的
（`run_blockers_has`、`run_no_item`、`run_field_has`）——
**每一次「測試放過了突變體」，答案都是「別看訊息，去看資料」。**

## 手刻的文法追不上真的文法，所以要明寫子集

**拒絕的替代**：把圍籬判斷「收成一份」就夠了。

上一輪把三份圍籬判斷收成一個 `visible_lines()`，並把停止條件訂成
「收成一份」。**那個條件訂錯了。** 一份手刻的 CommonMark 子集，
還是能被四種合法的 Markdown 繞過（每一種都 `--check` rc=0）：

| 寫法 | 規範怎麼說 |
|---|---|
| 圍籬裡示範一行 ```` ```python ```` | **閉合圍籬不能帶語言名**（CommonMark 4.5）。只看開頭就當成關，圍籬從中間裂開 |
| `<style>` 包住表格 | HTML block type 1，**瀏覽器根本不顯示** —— 讀者看不到的東西不是資料 |
| 四格縮排 | 是程式碼區塊。而上一輪為了「一到三格也算表格列」加的 `line.strip()` 把四格以上也一起吃了 |
| 表格列少了開頭的 `\|` | GFM 允許省略。我們靜靜丟掉整列（實測：點數少算、`Cancelled` 不見，而畫面上它還是一列表格） |

第一種還能反過來用：**把真的一列藏進去**，那比塞假項目更嚴重。

兩條出路：接一個真的 Markdown parser（要加依賴，而這是零依賴的 CI 閘門），
或者**明寫支援的子集、子集外一律報**。選了後者。
現在每一種都有訊息，而且訊息說得出「Markdown 會怎麼讀它、你該怎麼改」。

**「我看不懂」要說出來，不要猜。** 這一整份文件講的都是這件事，
只是這次的對象是 Markdown 本身。

## 同形字元：認形狀，不認清單

第六輪補了六個字元、第八輪又找到五個（U+23AF、U+31D0、U+2796、
U+2504、U+1173）。**清單永遠列不完，而每漏一個就是一個引用整段靜默。**

所以不再補清單，改成認形狀：兩個以上大寫字母 ＋ 一個不是連字號的東西
＋ 大寫字母加至少兩位數字 —— 那看起來就是一個 ID，只是中間那個字元不對。
訊息是「畫面上看不出差別，機器看得出來」。實測六份真實文件 0 誤報。

**「補清單」與「認形狀」的差別**，跟這份文件其他地方講的
「別再補一條 regex」是同一件事。

**2026-09-08 補完這件事的後半。** 認形狀那條加進來之後，`normalize()` 裡
還留著一串**非 `Pd`** 的相似字元清單（U+2212 減號、U+2500／2501 製表線、
U+02D7、U+30FC／FF70 長音、U+2043），也就是說「補清單」的做法其實還在，
只是被上面那條蓋住而看不見。

量過才刪：把那七個字元各造一次 `FE<字元>C01`，**認形狀那條一個不漏全部
抓得到**。所以刪掉之後不是「漏掉」，而是從「靜靜當成正確的 `FE-C01`」
變成「報一次，叫人改成 ASCII」。兩種都不是靜默，而後者不需要維護清單。

**沒有一起刪的**，因為量出來會產生靜默：

- `Pd` 類仍然折成 `-`（拿掉 14 條測試紅）—— 這是類別，不是清單。
- `Pd` 裡的 `〜`／`゠`／`〰` 仍然**排除在折疊之外**（拿掉 3 條測試紅）。
  折了的話 `FE-C01〜FE-C03` 會變成 `FE-C01-FE-C03`，而範圍文法只認 `–`。
- 變體選擇符仍然逐段剝除。外部審查建議「改用整類剝 `Mn` 就涵蓋了」——
  **這裡刻意不整類剝 `Mn`**：`Mn` 裡有越南文聲調與泰文母音符號，剝掉會
  讓兩個不同的詞撞成同一個（`ป่า` 與 `ปา`）。用「畫面上看不出差別」當
  理由的正規化，跨過那條線就變成把不同的東西讀成一樣。
- 全形英數仍然逐段折，**不用 NFKC**：NFKC 不折 en/em dash，卻會把 `①`
  折成 `1`。


## 測試搬到資料層之後，顯示層會裸奔

`--json` 以前**根本沒有 change 欄位** —— 那個關聯只存在於終端機表格，
網頁與 Excel 都看不到，等於這件事沒有被算過一次。補上 `changes` 之後，
測試改成斷言 `--json`（那是真相來源，對的）。

但突變體立刻證明：把終端機那一欄退回「只印第一個」，整套照樣全過。
**人不會去讀 `--json`。** 「同一個 ID 開了兩個 change」在畫面上隱形，
跟在資料裡缺席一樣糟。

所以兩層各要一條斷言：資料層問 `--json`，顯示層 grep `--all` 的輸出。

## 認太寬跟認太窄一樣嚴重

上一輪把「閉合圍籬」修對了，**開啟那一邊沒動** —— 而 CommonMark 對開啟
也有規則：縮排四格以上的不是圍籬（是程式碼區塊），反引號圍籬的語言名
不能含反引號。認太寬的後果比認太窄更糟：

    ```x`y                      ← 不是合法的開啟圍籬，我們卻當成圍籬
    | FE-C02 | 真的一列 | … |     ← 被藏起來
        ```                     ← 縮排四格，也不是圍籬

`--check` rc=0，那一列從表裡消失。**塞假項目至少總數會變，藏真資料連
總數都是對的。**

同一輪還漏了三種 HTML block（`<?…?>`、`<!X…>`、`<![CDATA[…]]>`）——
它們在瀏覽器裡是 bogus comment，完全不顯示，而我們把裡面的表格讀成資料。
以及 tab：CommonMark 的 tab 走到下一個 4 的 tab stop，而只數空白的話，
一個 tab 就能讓表格列變成程式碼區塊。

## 同形的不只連字號，字母也會

`FE-С99` 的 `С` 是西里爾字母 U+0421，`FΕ-C99` 的 `Ε` 是希臘字母 U+0395。
畫面上跟 ASCII 一模一樣，而 token 只認 `[A-Z]` —— 整個引用不存在。

跟「中間那個不是連字號」是同一件事，只是換個位置，所以判準也一樣：
**形狀對、但有字元不是 ASCII 就報。** 一條規則蓋住兩種。

順帶抓到一個舊病：形狀報警的前綴寫死 `[A-Z]{2,}`，而 `_GRP` 是 `[A-Z]+`
—— 三個字母的前綴（`API⎯W03`）整個不報。**同一支腳本兩種前綴長度。**

## 斷言指不到被測的事：第六種形狀

前五種在上面那張表。第六種：**斷言本身沒錯，但它測到的是另一件事。**

要測「縮排四格的假圍籬藏不住後面的表格列」，第一版把假圍籬插在兩列
中間 —— 結果對**正確的程式**也是紅的。因為任何非 `|` 的行都會結束表格，
那是 Markdown 的正確行為。那條測試實際測到的是「插入任何東西都會切斷
表格」，跟圍籬無關。

改成「縮排圍籬包住一個懸空引用」才真的能區分：正確的程式讀得到那個引用
並報「不存在」，突變體會把它消音。

**這一種比前五種好認**：它對正確的程式就是紅的，寫的當下就會發現。
前五種是默默變綠 —— 那才是要靠突變體才抓得到的。

證據是這一輪它改用一個真的 Markdown parser 當 oracle，一次就找出五個
——而前兩輪靠人列舉，每輪只找得到兩三個。

**「我列不出反例了」不是收斂，是列舉者的極限。**
這份文件其他地方講的都是「不要靠清單」，而停止條件本身也是一份清單。

## 模板與衍生專案的 `DECISIONS.md`，哪些分岔是宣告過的

`ai-team-starter`（模板）與從它衍生的專案各有一份 `docs/DECISIONS.md`，
兩份會分岔。**其中一部分的分岔是應該的** —— 這一節把「應該的那部分」寫下來。

**拒絕的替代**：要求兩份逐字相同（zero diff），專案專屬的決策用
`## [Local] …` 之類的前綴讓比對腳本跳過。

**為什麼不**：這份文件的體例是「拒絕的替代 ＋ 為什麼不 ＋ **證據**」，
而證據天生是專案專屬的（「第一次跑就抓到 42 條真實違規」「同一個 W8 在兩份
文件裡變成兩件事」）。逐字相同就得把證據刪掉換成空泛的宣稱 —— 而
〈「新增閘門要有真實事故」這條規則的正確讀法〉正是在要求證據。
**沒有證據的 `DECISIONS.md` 比分岔更糟。**

**也拒絕**：每次比對的時候人看一眼，判斷「這個差異有理由」。
那正是這份文件到處在消滅的東西 —— **依賴當下判斷的防線是 fail-open**。
今天判斷的人腦子裡有脈絡，三個月後看到 diff 的人沒有，
他要嘛蓋過去要嘛不敢動，兩種都會讓分岔繼續長。

**改成**：分岔照樣量，但**允許分岔的類別事先宣告**，
量出來的東西只分成「在宣告的三類裡」與「不在」，沒有第三種答案。

### 怎麼量

兩個 repo 都在本機的話：

```bash
python3 - <<'PY'
import pathlib, re, difflib
A = pathlib.Path("../ai-team-starter/docs/DECISIONS.md")   # 模板
B = pathlib.Path("docs/DECISIONS.md")                       # 這個專案
PFX = [("APP-","P1-"),("DEP-","P2-"),("app-","p1-"),("dep-","p2-")]  # 依你的前綴改
def norm(s):
    for a,b in PFX: s = s.replace(a,b)
    return s
def sections(p):
    parts = re.split(r"(?m)^(## .+)$", norm(p.read_text(encoding="utf-8")))
    return {parts[i].strip(): parts[i+1] for i in range(1, len(parts), 2)}
a, b = sections(A), sections(B)
print(f"只在模板：{sorted(set(a) - set(b))}")
print(f"只在本專案：{sorted(set(b) - set(a))}")
for k in sorted(set(a) & set(b)):
    if a[k] != b[k]:
        n = sum(1 for l in difflib.unified_diff(a[k].splitlines(), b[k].splitlines(), lineterm="", n=0)
                if l.startswith(("+","-")) and not l.startswith(("+++","---")))
        print(f"內文分岔（{n} 行）：{k}")
PY
```

**前綴那張表要照專案改** —— 而且要注意兩件實測到的漏網：
非斷字連字號 `‑`（U+2011）與底線分隔的寫法（`DEP_G01`）都不會被上面的
`replace` 蓋到，會變成假陽性。看到只差一兩行的分岔先確認是不是這兩種。

### 宣告過的分岔只有三類

| 類別 | 判準 |
|---|---|
| **證據段** | 專案引用自己的真實事故或具體例子，模板沒有那個事故，只能寫成泛化的說法 |
| **例子的前綴與名詞** | 模板用中性的 `APP-`／`DEP-`／「外部服務」，專案用自己的 |
| **專案專屬的整節** | 那個決策只對這個專案成立，模板沒有對應的概念 |

**衍生專案要在這一節底下列出自己的完整清單，不是列幾個例子。**
列例子沒有用 —— 上面那段量出來的結果要能跟清單**一對一對照**，
才有辦法回答「這一條在不在宣告裡」。剛從模板複製的專案清單是空的。

**這三類以外的分岔一律要修**，而且**修的方向是往模板對齊** ——
共用治理腳本的規則，真源在模板；專案可以加自己的節，不可以改共用節的規則。

實測過一次反例：補完節標題缺口的那一輪，改寫模板版措辭時沒回寫專案版，
**在修漂移的動作裡製造了一條新漂移**。所以修完要再量一次，不能只量一次。

**代價**：這不是閘門，沒有東西會自動跑它 —— 因為 CI 看不到另一個 repo
（同〈`check-ruleset.sh` 不接進 CI〉的理由：判準是**權限**，不是重要性）。
它是同步兩邊時要跑的一步，寫在這裡是為了讓「有理由」變成一份可以被 diff 的東西，
而不是每次重新判斷一遍。

## 拆掉的閘門，以及拆掉之後少了什麼

2026-09-08。上一段量出「治理層是產品的 5.2 倍」之後的處置。**每一條都寫出
「拆掉之後，什麼東西沒有人看了」** —— 只記拆了什麼，六個月後會有人以為那件事
還有機器在管。

### `test-ci-workflow.sh`（350 行手寫 YAML parser）→ `actionlint`（固定版本）

它存在的理由是一條規則：**`${{ }}` 不可以直接插進 `run:`**。那正是 actionlint
的 `expression` 規則，而且它做得更準（會指出欄位位置）。實測對照 —— 同一份
`ci.yml` 把插值放回去：

```
.github/workflows/ci.yml:64:84: "github.head_ref" is potentially untrusted.
avoid using it directly in inline scripts. instead, pass it through an
environment variable. [expression]
```

**現成的靜態檢查器做得到的事，不要自己寫一份。** 自己寫的那份要自己養：
它有 24 條斷言、自己的自測、而且每次 `ci.yml` 改結構都要跟著改。

**少了三類檢查**（實測確認 actionlint 對這三類 rc=0）：

| 少掉的 | 原本擋什麼 | 現在靠什麼 |
|---|---|---|
| 整份檔案不得出現 `continue-on-error` | 讓紅掉的閘門不算失敗 | PR review |
| job 層不得有 `if:`／`defaults:` | 整個 job 被 skip 而算通過；用 `defaults.run.shell` 一次中和 | PR review |
| `Lint`／`Typecheck`／`Test`／`Build` 的 `run` 必須剛好是那一句 | 把 `Build` 改成 `run: true` | PR review |

**為什麼接受**：這三類只可能出現在動 `.github/` 的 PR，而動 `.github/` 一定
是 `governance/` 分支（分支閘門擋著），那種 PR 的 diff 上會直接寫著
`continue-on-error: true`。判準是〈已知的治理層技術債〉那條：**這個缺陷現在
放得進什麼真的損害？** 答案是「一個人要在一份給人審的 diff 裡寫下那一行，
而且要有人按下 approve」。

### 第八欄「涵蓋證據」→ 標記欄的一個 `Done` 列舉值

那一欄是**為一列造的**：全 repo 只有 `APP-O10` 在用。支撐它的是
`progress.sh` 裡 23 處、`parse_evidence()` 約 45 行、`_commit_state()`、
`test-progress-check.sh` 裡 10 條斷言，加上「第八欄表頭只能是『涵蓋證據』」
那條表頭規則與 `AGENTS.md` 一整段。

**但不能直接刪。** 它解的盲區還在：治理工作在結構上不可能有同名的 change
（改 `.github/` 只能走 `governance/`，而 `governance/` 不准碰 `openspec/`），
刪掉之後 `APP-O10` 會從「已完成」變回「未開始」—— 那是**反方向的錯**，
WBS 對人說謊。

所以改成在**既有的**標記欄加一個列舉值 `Done｜理由`。標記欄本來就有 parser
與測試（封閉列舉 ＋ `｜` ＋ 理由），加一個值等於加一行。

**少了什麼**：`commit` 存不存在、有沒有合併，不再有機器驗。接受的理由是
**原本那條規則自己的文件就寫著**「機器只證明了那個 commit 存在而且已經合併，
沒有證明它在語意上真的做完這一項，那一格仍然要人讀 diff」—— 既然結論本來就
要人讀，把「SHA 格式對不對」機器化的價值很低。

**沒有一起放掉的**：`Done` 跟 change 並存會報「矛盾」。人手寫的事實與算得
出來的事實同時存在，就是兩個來源，而兩個來源一定會漂 —— 這一條保留為機器規則。

### `check-scenario-coverage.sh` 從閘門降級成報告

它證明得了的事只有「這個 ID 出現在一個通過的測試標題裡」。**當它是閘門，
唯一保證會發生的事是「補一條標題帶 ID 的測試」** —— 那比沒有閘門更糟，因為
它會產生已經驗過的外觀。

現在：有缺口也回 0、不接在 CI 上，只在 `prompts/05-verify.md` 那一步要求把
清單原文貼出來、對每一條說出處置。**退出碼 2 保留給「量不到」** ——
測試沒綠、報告產不出來、一份規格檔都掃不到；那三件事跟「沒有缺口」不一樣。

跟著一起拆掉的是整套豁免文法：封閉列舉的種類（`vitest`／`playwright`／
`command-negative`／`ci-job`／`manual-browser`）、`ci-job` 的證據要對得上
`ci.yml` 的步驟名、`manual-browser` 的證據要含 40 位 SHA 且在 HEAD 歷史裡、
孤兒豁免、過期豁免、重複豁免。**那是一整套為了「怎麼合法地不驗」而生的規則**
—— 閘門不在了，規則就沒有依附的東西。`- **VERIFY-BY**` 那一行留著，但**只是
寫給人看的註記**：報告會把它原文印在缺口旁邊，沒有任何機器意義。

**少了什麼**：一條 Scenario 進 `openspec/specs/` 之後沒有測試，不會再有東西
變紅。靠 `prompts/05-verify.md` 那一步的人。

## 沒有手寫的架構總覽，架構視圖是推導出來的

2026-09-12，在衍生專案（41 份 spec、49 份 design.md）上定的，兩個外部審查者兩輪共識。

**拒絕的替代**：一份手寫的 `ARCHITECTURE.md`，列每個 capability 做什麼、彼此怎麼依賴。

**為什麼**：`docs/WBS.md` 能活著是因為 `progress.sh --check` 用 ID 驗它、CI 會紅。
一份散文總覽沒有這種檢查，衍生專案的 ROADMAP 已經示範過一次（兩張總覽表沒跟著改，
「頂端加了警告也沒用」，最後刪掉）。推導出來的引用圖只能說「現狀是什麼」，說不了
「邊界不該是什麼」—— 所以「不該是什麼」留在 ADR 裡由人寫，每條標**誰在擋**（`邊界狀態`），
`arch-view.sh` 讀出來。

**同時拒絕的**：metadata 由 CI 驗（寫個字串就過）、PR 勾選框（空殼）、每條 design 決策
加分類欄（真正的邊界十來條，全填就是空殼資料）、實作中把需求寫回 artifact（這裡規格先凍結）。

## 地圖先於 change：新專案從整張 WBS 開始，孤兒 change 是違規

**2026-09-12，兩位外部審查者（gpt-5.6-sol、Gemini 3.1 Pro）兩輪共識。**

### 問題

模板的流程從第一步就是逐功能的：`01` 開頭是「我要開始一個新功能」，`02` 直接
propose 一個 change。`docs/WBS.md` 是「選用」，機器驗它的東西全在（`--check`、
ID 命名、`--render`、只有 `governance/` 能動），但沒有任何一步會帶你去寫第一份。
衍生專案有地圖，是因為負責人一開始手上就有一份 Excel，不是流程產的。
另一個專案用逐功能的 brainstorm → plan 起家，現在的症狀：每份 plan 是孤島、
串不起來、不知道下一步、文件老化。

### 決定

1. **`prompts/00-map.md`，每個專案跑一次**：問全貌，攤成非空的 `docs/WBS.md`
   （七欄、〈阻塞類型〉表、進度區塊標記、結果型里程碑），走 `governance/` 進 main，
   **第一個會合併的 change 之前**。`01` 改成「一個工作項目的探索」：先選 ID、看阻塞、
   跑 `progress.sh --all` 與 `arch-view.sh`，再問。`02` 在 propose 前要求 change id
   以 WBS ID 開頭。
2. **地圖只放問題，不放解法。** 寫交付結果、順序、依賴；不寫系統怎麼切、不列未來的
   capability、不畫依賴箭頭。理由是衍生專案的反證：地圖上「資料層」一項，change 拆成
   兩個 capability，**規格對、地圖不用改** —— 因為它寫的是結果不是切法。第一天若有
   非決不可的邊界，寫一條具體的 Proposed ADR，其餘交給 `arch-view.sh` 推導。
3. **粗細：全局覆蓋、近期細化。** 下一個里程碑拆到可開 spec PR；後面只留結果型一列，
   點數 `—`。停止拆分的判準不是列數：知道下一個可開的 change、知道它需要什麼、
   主要流程沒整段消失、沒假裝知道內部怎麼切。
4. **對不上任何 WBS ID 的 change 是 `--check` 的違規**（以前只印紅字、不影響退出碼）。
   `spec/<id>` PR 在規格階段就紅 → 先開 `governance/` PR 改地圖。**沒有 WBS 的專案不驗**
   （舊專案相容）。零例外：spike 不進 repo、純工具走 `chore/`、從別處搬來的先進地圖。
5. **`spec/` 仍不能改 WBS。** 地圖的變動要單獨被看見。但縮小「必須改」：capability
   內部拆分而交付結果沒變 → 不改；結果／順序／依賴／範圍改了、或文字仍宣稱已被推翻的
   邊界 → 提案者開最小 governance PR，`/opsx:apply` 前合併。
6. `progress.sh` 一般輸出加〈工作拆分〉（一個 ID 對多個 change 列出來，不擋）。

### 第 4 條是一條新的閘門 —— 憑什麼加

（第一版寫「rc 凍結『不得新增 gate』的具名例外」—— 那條凍結是 `ai-project-starter`
（v1.0-rc.5、單人階段閘的那個 repo）的規則，**這個 repo 從來沒有**。討論時把它當前提
是搞混了兩個 starter；結論沒受影響，因為這裡本來就有自己的判準，就是下面這條。）

不是「標準流程」四個字壓過規則，是這條符合〈「新增閘門要有真實事故」〉的判準：
繞法在測試 repo 跑得出來（`test-progress-check.sh`〈孤兒 change〉：有地圖、開一個 id
不在地圖上的 change、CI 綠、地圖靜靜過期），檢查精確（字串前綴對 ID），不需要 metadata
或勾選框，衍生專案 49 個 change 零孤兒、升嚴不追溯破壞。**這不是「標準流程可以隨意加閘門」的先例** ——
下一條閘門一樣要先把繞法在測試 repo 跑一次。

### 拒絕的

- **只靠 prompt 前置條件（「找不到 ID 就先改地圖」）**：這個 repo 的歷史是 AI 有 Bash 就會
  繞過 prompt；前置條件是自律，不是約束。留著它，但不能是唯一的保護。
- **把孤兒清單寫進 `--render` 的進度區塊當提醒**：孤兒是該擋在 main 外面的違規，
  把暫態違規寫進版控的區塊會重演「為了顯示而漂」。
- **內建空的 `docs/WBS.md` 骨架**：空表過得了 `--check`，等於一個「已規劃」的外觀。
  範例放在 `00-map` 的圍籬裡，由 prompt 產第一份有真實內容的。
- **地圖列預期 capability 與依賴箭頭**：剛拒絕過的手寫架構總覽換了個容器。
- **一個 WBS ID ＝ 一個 change ＝ 一個 capability**：不是規則，機器也不該驗它。
- **禁止 superpowers**：它是功能層工具（brainstorm 輔助訪談、plan 想一項怎麼做），
  問題不是工具，是拿多份互不相連的 plan 當總體計畫。寫在 `00-map` 尾註。

## archive 前的雙模型審查：影子先於閘門，change 先於 PR

### 問題

當一個 change 的每個 slice 都由同一個作者（人或 agent）寫、逐個 PR 由同一個人合併，
沒有任何一步把整個 change 攤開來看：單一 slice 的 review 看不到跨 slice 的不一致、
規格說了但沒有任何 slice 做的缺口。CI 驗的是「這個 PR 沒違反規則」，驗不了「這個 change 做的是規格說的東西」。

### 決定

`.github/scripts/archive-review.sh`＋`prompts/06-archive-review.md`：`tasks.md` 全勾之後、
`/opsx:archive` 之前，把 change 的全部（origin/main 上凍結的規格、WBS 那一項、DECISIONS 相關整節、每個 slice PR 的
diff —— 排除 lockfile 與 archive 目錄，任一個拿不到就整輪不算 —— 與說明）打成一包，**平行**送兩個模型各審一次；結論只有三種標籤；需修正的回原 session 修，
回審**一次**；每一條需修正由人判定（誤報／已驗證／已修）、記進帳本。**影子試跑，不阻塞。**
升阻塞的條件有四個維度 —— 凍結的樣本數（最早 N 個兩個模型都回答的 change）、經人工判定「已修」
（重現了、而且那個 change 回審過）的需修正數、誤報率、每個 change 的等待 P90 —— **數值只寫在腳本頂端一處**，
`--report` 印出來；這裡不重複（〈「新增閘門要有真實事故」〉：寫在文件裡的數字會漂）。
全部成立才討論升阻塞；不成立就整套刪掉。

這是模板的共用治理腳本：真源在這裡，衍生專案逐字拿（〈模板與衍生專案的 `DECISIONS.md`〉）。

### 拒絕的

- **裝一個多 agent 編排工具**（manager 派工、A 審 B 自動回圈、共享 workspace）：對一人合併的專案，
  「更多 PR、更盲目」是惡化不是改善；瓶頸是沒人審產品層，不是吞吐量。現有 `codex exec`／`agy --print`
  加一支組 bundle 的腳本就夠。重新考慮的條件：串接／重試／權限的 shell 已經難維護。
- **每個 PR 都送兩個模型審**：一天幾十次、每次幾分鐘；而且單一 slice 看不出跨 slice 的不一致。
  **澄清（2026-09-19）**：拒絕的是 repo **強制**、每個 PR 必跑、當合併閘門的版本；不禁止統整者對具體問題不確定時臨時送外審。臨時送審不進本節的樣本、模型結論不具阻塞權、停止契約在 `prompts/08-pr-review.md`（見〈2026-09-19　外部 PR 審查是例外〉）。
- **一開始就當閘門**：依〈「新增閘門要有真實事故」〉，還沒有一條可重現的「它抓到而 CI 沒抓到」之前，
  阻塞是臆測。而一個大家都會跳過的閘門比沒有閘門更糟。
- **用 commit 訊息 grep 找 slice**：同一個 WBS ID 可以有多個 change，主旨提到它的 WBS 列、spec PR、
  兄弟 change 都會混進 bundle（實測：三個 commit 裡只有一個是實作）。改用合併 PR 的分支名
  `feat/<id>[--…]`、`fix/<id>[--…]`；拿不到 PR 清單就這一輪不算數，不是靜靜降級。
- **用 merge commit 的 `git show` 當 slice 的 diff**：只有 squash 合併時它才等於整個 PR；
  repo 允許 merge commit 或 rebase 的話會漏。diff 從 `gh pr diff` 拿。
- **報告只算已判定的發現、任一模型回答就算樣本、「已驗證」就算修好、跑到成立為止**：
  四個都是可以把數字做出來的洞。改成：還有需修正沒判定就不下結論；只有兩個模型都回答的
  change 才是樣本；升阻塞數的是「已修」（人判定重現了、而且那個 change 回審過）；樣本是最早的 N 個。
- **移走 `r1/` 重跑**：帳本說某個模型答過、檔案卻不在，腳本拒絕 —— 重跑只補沒回答的那個模型，
  答過的不重送、**沿用同一輪的 bundle 與 main.sha**（兩個模型要看同一份），樣本順序不會因此改變。
- **「答過」只看檔案**：CLI 非零或逾時可能留下格式完整的半成品。「答過」＝那一輪帳本 ok **且** 檔案有回答；
  兩者不一致就拒絕，不猜。
- **用 `r2/` 目錄存不存在判「第三輪」**：diff 拿不到、模型缺席都會留下目錄，下一次就被當成第三輪永久卡死。
  「只准一次」看的是兩個模型都答過第二輪；沒答的可以補跑。
- **「有一行像回答」就算答過**：第二輪五條只答一條、第一輪結論寫 3 條但明細沒有，都會被記成算數、鎖死回審。
  改成：第一輪結論的三個數字要等於明細裡的標籤數；第二輪每一號都要有 `N. 已修／未修／改壞了別的`。
- **一個模型答完第一輪就能開第二輪**：第二輪 bundle 列的是兩個模型的需修正，另一個之後補完的發現進不來。
  兩個第一輪都答完才能回審。
- **樣本從「現在還通過檢查的檔案」重算**：前十名之一的檔案壞了，第十一個會遞補進來，等於換樣本。
  改成先照帳本凍結前 N 名，再驗檔案；壞了就不下結論、不遞補。
- **第二輪同一號出現兩次照算**：`1. 已修` 與 `1. 未修` 並存時，先出現的會被當答案。每一號恰好一次，否則那份不算。
- **判定不綁第一輪是否算數**：半成品先判、重跑蓋掉後舊判定套到別的發現上。`--judge` 先驗該模型第一輪 has_answer。
- **`--judge` 的「第幾條」收任何數字**：`01` 過得了範圍檢查、躲得過「判過了」的比對、寫進帳本又變成 `1`，
  同一條算兩次。只收正整數的標準寫法；報告看到同一條兩筆判定就不下結論。
- **`gh pr list --limit 1000` 靜默截斷**：舊的 slice 漏掉、bundle 卻照樣成為樣本。剛好 1000 筆就這一輪不算數。
- **bundle 上限 700 KB**：gemini 的 prompt 走命令列參數（`agy` 不吃 stdin），Linux 單一參數上限 128 KB、
  macOS 整條命令列 1 MB —— 700 KB 是編出來的數字。改成照命令列容量算（數字只在腳本裡）；codex 改走 stdin。
- **帳本記 bundle／回答檔的 SHA-256、判定記 finding 原文的 digest、第二輪綁兩份第一輪的 digest 父鏈**
  （第 19 輪外部審查要求）：它守的是「檔案被換成另一份同數量的回答」—— 那是竄改，不是誤操作；
  上面〈沒有的〉已宣告不防竄改，而且一個人合併的專案裡竄改自己的試驗量尺沒有對手。
  加上去的代價是每個入口都要重驗 digest、帳本 schema 再長一倍，守一個沒有對手的威脅。**拒絕。**
  留下的信任邊界：誤操作與半成品（移走、沒答完、格式不對、判錯條、同時跑兩次、逾時殘留行程）全部 fail-closed。
  第 20 輪指出一條**不是竄改**的路徑：父行程先退、忽略 TERM 的後代被 reparent 後躲過升級 KILL，還握著回答檔的 fd。
  關法不是 digest：每次送出寫**這一次獨有的暫存檔**，跑完才**複製**（cp，換 inode；mv 不換，rc=0 卻留下握著
  stdout 的子行程時 mv 發布的就是它握的那個檔）成回答檔，逾時那份永不發布。
  第 22 輪再指「cp 讀到 EOF 前孤兒追加輸出」：追加任何非空內容都讓第一輪「結論是最後一個非空行」不成立、
  第二輪追加編號行就重號 —— 要嘛作廢重送，要嘛判定讀的行一字不變，**改不了報告的任何一個數字**。
  Gemini 3.1 Pro 與 Claude Opus 4.6 各自逐類驗過，同意不加鏈；codex 維持要求，記在這裡。
  教訓：對抗審查的停止條件要問「哪個可觀測輸出會錯」，不能問「bytes 能不能寫進檔案」—— 後者永遠有更窄的時間窗。
- **模糊的命令列與文法**：`--rereveiw` 悄悄變第一輪、`--report foo` 忽略多餘參數、`ARCHIVE_REVIEW_TIMEOUT=abc`
  讓 watcher 永遠不逾時；第一輪結論只要「某一行有三個數字」、第二輪「已修但其實不確定」算已修、多出第 N+1 號照算。
  全部改成封閉列舉、固定格式、fail-closed。
- **逾時只 kill 父行程**：子行程繼續寫回答檔，寫進的是下一次「沿用」會讀到的檔案。殺整棵樹、升級 KILL、收割；殺剩的靠暫存檔隔開。
  同一 change 同一輪同時跑兩次會互相蓋檔：`mkdir .lock` 當鎖。
- **slice 的 merge commit 不在釘住的 main 上就「略過」**：fetch 與 pr list 之間有人合併時 bundle 會不完整卻照算。exit 2。
- **`--report` 從帳本抄數字**：帳本說答過、檔案卻不在或不完整，報告照算；判定「已修」之後把第二輪檔案刪掉、
  截短、改成未修，報告照樣把它算進升阻塞的數。改成**帳本是索引、檔案才是證據**：每個數字從回答檔重算，
  每一條「已修」回頭驗第二輪三件事（ok 的 row、1..N 全答、那一號寫已修），證據不成立就不下結論。
- **「回審過」就算「已修」**：第二輪存在不代表那一條修了。第二輪 bundle 把需修正逐條編號，模型照編號答
  `N. 已修／未修／改壞了別的`；`--judge … 已修` 查那個模型對那一號寫的是不是「已修」。
- **規格從 working tree 讀**：凍結的是 main 上那份；working tree 可能正在改。從 `origin/main` 讀。
- **diff 拿不到就印「拿不到」繼續送**：少了實作內容的 bundle 不能進樣本。任一 PR 的 diff 拿不到就 exit 2、不寫帳本。
- **升阻塞的數值散在腳本、AGENTS、DECISIONS**：四處會漂成四個答案。只在腳本定義一次。
- **忽略整個 `.local/`**：會遮住衍生專案未來放在那裡的別的東西。只忽略它自己的兩個路徑。
- **回審不限次數**：第三輪就是流程在製造等待。腳本拒絕 `r3`。
- **第一輪兩個模型互相看對方的結果**：加一層協調，多一種「兩個都被同一個誤導帶走」的失敗；
  獨立審比較便宜，判斷留給人。（第二輪不同：回審的對象就是兩個模型的需修正清單，一起編號給雙方。）
- **帳本進版控**：它是試驗的量尺，結算完就刪；進版控會變成沒人維護的第二份審查紀錄。
- **只讀 squash commit 的內文、不拿 PR 說明**：squash 內文是各 commit 訊息的串接，
  PR 裡寫明的「刻意取捨」不在裡面 —— 實測少了它，模型把刻意的事標成需修正。

### 沒有的

- **不防惡意竄改。** 帳本與回答檔都在本機、gitignore、負責人自己改得到。這套守的是誤操作與模型的半成品
  （移走重跑、沒答完、結論跟明細對不上、判定套到別的發現上、樣本被遞補）；一個人合併的專案，
  竄改自己的試驗量尺沒有對手。升阻塞仍由人看 `--report` 與檔案決定，不是腳本自動升。
- 它證明不了瀏覽器裡的樣子（bundle 只有程式碼與規格）；提示明寫這一點，叫模型不要猜。
- 兩個模型都不在的機器上，它明說跳過，不假裝審過。

## 入口文件清不清楚，用沒有脈絡的模型實測，不用作者自己讀

2026-09-13。負責人問「LLM 看到就知道該怎麼做嗎」。作者讀一遍會覺得清楚，因為作者知道答案。

## 多模型分工工具進模板目錄，不做 npm 套件也不用 subtree

2026-09-13 三方共識（agy opus-4-6／Gemini 3.1 Pro／codex sol）。

**決定**：多模型派工與票流程腳本（`lib.mjs`、`write.mjs`、`council.mjs`、`ticket.mjs`、`setup.mjs`）直接進模板（舊：`.github/scripts/llm-team/`）目錄出貨。

**拒絕的替代**：
1. **獨立 npm 套件**：發布到 npm 會引入打包構建、版本相依與安裝門檻，且這套工具目前僅在真實專案跑過三張票，過早承諾套件 API 與語意版本維護是負擔不是資產。
2. **git subtree / git submodule**：衍生專案複製模板時一向是一次性複製乾淨目錄（不含 submodule/subtree 複雜度），增加 git 操作複雜度且可能被分支閘門絆倒。
3. **只留在特定衍生專案**：在 web-agency-system 實測證明有效，但多專案各自維護腳本會立刻重演代碼漂移與錯誤判定。

**為什麼**：
- **零相依、複製即用**：只用 Node.js 內建模組（`node:fs`、`node:path`、`node:child_process`），無需額外 npm install 即可運作。
- **更新怎麼傳**：模板 repo 是單一真源，衍生專案以「逐字拿」方式同步腳本檔案。專案特有設定（模型 ID、指令白名單、worktree 路徑等）全部集中在 `config.json`，那是專案唯一該修改的設定檔。
- **治理白名單決定**：同時將 `.claude/skills/` 納入 `check-pr-branch.sh` 的 `governance/*` 白名單。理由：它與 `prompts/` 同性質，皆為給 LLM 的操作規則（模板出貨的一部分），修改 skill 同屬改動流程與治理層，應允許在 governance PR 中維護。

### 2026-09-13 修正：程式真源移到維護者的 config repo，模板只放唯讀快照

三方三輪共識、Fergus 定案。llm-team 的程式只有一份可編輯真源（維護者私人 config repo `home/skills/llm-team/`）；模板放的是唯讀快照 `.agents/skills/llm-team/`（舊：`.github/scripts/llm-team/`），由真源的 `export.mjs` 產生，帶 `VERSION`、`SOURCE.json`（記來源 commit）與 `MANIFEST.sha256`。

**沒有的**：

## 2026-09-14 全系統預設 pnpm

Fergus 定案（起因：發現衍生專案 GuildHub-frontend 用 npm——「pnpm 就是要節省資源，結果別的專案用別的方式，這樣就失去初衷了」）。

**決定**：模板與所有衍生專案一律用 pnpm，不用 npm。`package-lock.json` → `pnpm-lock.yaml`（`pnpm import` 產生）；`package.json` 加 `packageManager` 欄釘死版本；CI 與 `.github/scripts/` 的安裝／執行指令全面改寫（`npm ci` → `pnpm install --frozen-lockfile`、`npm run`／`npm test` → `pnpm run`／`pnpm test`、`npx <lockfile 鎖住的 CLI>` → `pnpm exec <CLI>`、`npx <一次性遠端套件>` → `pnpm dlx <套件>`）；`llm-team.config.json` 的 `allowCommandHeads`／`installCommand` 同步改 pnpm 系。

**為什麼**：pnpm 省的是**同一台機器多個專案共用 content-addressable store**（不同 repo 各自一份 `node_modules` 是重複磁碟佔用）＋**嚴格性**（預設不做 hoisting、不放行 phantom dependency——沒宣告的相依會直接解析不到而炸掉，這對 LLM 寫的程式碼是額外一層守門）。它**不**省測試記憶體／CPU／Vercel 建置額度／LLM API 額度——這幾類問題各有自己的解法，不要拿「統一 pnpm」去頂替。

**遷移順序**：先改這個模板（不改的話，下一個從模板複製出去的衍生專案又會生出 npm），衍生專案再逐字跟進，不回頭改。

**`lockfile-lint` 拿掉的理由**：5.x 版只認 npm／yarn 的 lockfile 格式，不認 `pnpm-lock.yaml`。等價的閘門改成直接掃 `pnpm-lock.yaml` 裡有沒有非 `registry.npmjs.org` 來源的 resolution（`tarball:`／`repo:`／`commit:` 這幾種欄位只會出現在非 registry 來源；一般套件只記 `integrity`）——邏輯跟 `lockfile-lint --validate-https --allowed-hosts npm` 等價，只是換一種格式去驗同一件事。

**拒絕的替代**：
1. **只改衍生專案，模板留 npm**：模板是所有新專案的起點，留著 npm 會讓「系統統一用 pnpm」這件事每次複製模板都要重做一次，而且下一個忘記的人會直接把 npm 傳下去。
2. **兩種套件管理並存（依專案自選）**：拿統一 pnpm 換取的 content-addressable store 共用，只有全部專案都用同一套管理工具才成立；並存等於沒有統一。

**沒有的**：
- **不代表任何效能保證**：這條決定省的是磁碟與嚴格性，不是速度或成本；不要拿它當其他效能問題的答案。

## 2026-09-19　外審的終止依據是驗法不是意見；回審仍只准一次，粒度仍是一個 change

**決定**：`archive-review` 的「一次回審」不放寬。改的是**停下來的依據**：第一輪每條「需修正」附的驗法必須寫出**預期結果**（`驗證：<指令或操作> → 預期 <結果>`），沒有預期結果的只能標「誤報候選」；第二輪只判「上一輪每條自己附的驗法在這次 diff 上會不會過」——會過 `已修`、不會 `未修`、會過但別的閘門壞了 `改壞了別的`、驗法跑不出來 `未修 — 驗法無法執行` 交人；**第二輪不重新評價發現對不對、不新增發現**。人工 `--judge 已修` 的意思明確為**修前重現得到、修後驗法達到預期、回審過**，不是「修後會過」——否則本來就會過的誤報會被算成 verified miss，灌大 `MIN_VERIFIED`。批次粒度維持**一個 change**；校準用既有的 `--report`（`TRIAL_N=10`），不加欄位、不加工具。改動只有 `prompts/06` 的措辭與腳本裡「已修」的定義文字，腳本邏輯、`AGENTS.md`、流程圖都不動。

**來源**：使用者顧慮（2026-09-19 原話）：「只回審一次會不會不夠準，因為還沒討論出答案；但是有時候的確花太多時間。我們先自己開發，開發完再讓等級高的模型去審，不要每個部分開發完就審，累積多一點再一起檢查，讓他們做最後的確認就好。」對照資料：GuildHub 09-13～09-19 歸檔 16 個 change，`archive-review.sh` 一次都沒跑，同一段時間三個 PR 卻跑了 21 輪沒設計過的 PR 級輪詢（見上一節）——**設計好的 change 級批次審查沒在用，沒設計的 PR 級輪詢跑滿**。使用者要的「累積再一起檢查、最後確認」就是 `archive-review` 原本的形狀。

**為什麼一次回審夠**：「還沒討論出答案」只有三種：（a）發現對、沒修到位——驗法還是紅的，`未修`，回去修、本機重跑驗法，不用再問模型；（b）發現錯、統整者反駁對——驗法在它宣稱的前置狀態下重現不了，就是誤報，人一句話結案；（c）規格解讀不同——不是程式對錯，模型沒有規格決定權，人選一個解讀改規格或標可接受風險。三種都不是多一輪能解的；第三輪增加的是意見，不是可判定的新證據。套回 21 輪事故：每個 PR 最晚第 2 輪停，三個 PR 上限 6 輪。

**校準迴路**（回答「要不要補校正」）：校正不是再加一道審，是看帳本。主數字是**有 verified miss（人工 `--judge 已修`）的 distinct change 數**，不是帳本列數——同一問題兩個模型都報只算一個 change。最早凍結的 10 個樣本若不到 `MIN_VERIFIED=2`，依既有契約是**刪掉這套**，不是「少問一點」。更便宜、不用問模型的訊號：突變測試在「完成」時仍有存活（`survivors > 0`）就直接否定「已經沒問題」。

**拒絕的替代**：

1. **放寬到兩次或三次回審**：見上面三種情況；21 輪就是「審到沒意見為止」的結果。
2. **跨 change 累積（里程碑 3～5 個 change 一起送）**：上下文過載（模型把前一個 spec 套到後一個 diff）、規格層的錯越晚發現返工越大、帳本與 r2 編號與 `/opsx:archive` 都以 change 為生命週期；而且事故是「change 級流程被繞過」，不是「change 級呼叫太多」，沒有事故支持跨 change。
3. **改腳本讓作者把驗法的執行輸出貼進 r2 bundle**：r2 模型只是預篩，真正算數的是人工重現後的 `--judge`；不值得為預篩改腳本。r2 據 diff 推論驗法過不過，誤判的代價只是提早交人。
4. **「某一類需修正反覆出現就把那一類提前到 PR 級用 08 問」**：帳本沒有 category 欄位，現在沒有任何樣本，加約定沒有事故依據。等第一份 10 個 change 的 `--report` 出來再看；若要做，用 finding id 約定 `<change-id>/<08 的四類之一>/<序號>`、以 id 第二段分組，不加欄位；而且即使成立也只約束「已經因不確定而啟動的 08 要先看那一類」，**不自動增加送審次數**——否則校準迴路會把 21 輪帶回來。
5. **主導模型換成更強的模型來降低審查需求**：額度扣太快，開發沒多少就沒了；而且慢的根因是流程誤讀，不是模型能力。主導模型是可量的參數，不在本節決定。

**推翻條件**（任一成立就回來改本節）：取本節上線後**最早 10 個**兩模型都答完、且照「初審＋一次回審」跑完的 change——
- codex：其中 ≥2 個在回審結束後仍留下**可重現**的 material escape（後續 PR 留言有 08 四類標籤、對得回原 change、驗法在回審結束時的版本上失敗、問題當時已存在）。若這 2 個都要跨多個 change 才能重現，同時推翻「單一 change 粒度」。

## 2026-09-25　依賴圖（P1）：排程逆序搬到〈跨項依賴〉並給它文法；上一節寫的 P1 做法前提錯了

## 2026-09-25　里程碑可追溯性（P2）：報告不擋，預設就印一行；不做差異

**決定**：`progress.sh` 算出哪些 **WBS ID** 沒有被任何里程碑的「靠哪些」指到（`--json` 的 `milestone_trace`）。**報告，不擋**：再多都不影響 `--check` 的退出碼。不叫「100% 法則」——它只證明有一條引用邊，證明不了語意上真的涵蓋，也證明不了沒有漏掉還沒寫進 WBS 的範圍。
- 單位是 WBS ID（續行列沒有 ID）；不算 `Cancelled`／`Regular`；**不用週次截斷**（已細化但還沒排週次的工作會被靜默排除）。
- 分兩組：① 已排週次卻沒被指到；② 沒排週次／遠期而沒被指到。
- 三態：正本四欄 → `available`＋清單；舊的兩欄 → `unavailable`、清單是 `None`（**不是 `[]`**）；沒有〈里程碑〉→ `no_milestone_section`。
- **預設輸出就印一行摘要**（含 `--check`；`--json` 不印，免得弄壞下游解析）：`① N 項…；② M 項…（--trace 看是哪些）`；全部被指到時印「N 項全部被某個里程碑指到」；舊格式、解析不出來、沒有〈里程碑〉各自印「未評估（原因）」。一份沒有人跑的報告，就是「機制沒起作用、沒人知道」的形狀；零項也要講，不然「沒問題」跟「沒看」長得一樣。細節在 `--trace`。

**拒絕的**：「遠期那組印本次新增／移除的差異」（codex 第二輪提的）——差異要跟某個基準比：跟上一次比要存狀態檔（這個 repo 明文不放分支推的狀態、「算出來的，不是寫出來的」）；跟 `origin/main` 比要把整個解析再跑一次，而且離線、shallow clone 拿不到。codex 要的效果是「避免每次重讀大坨靜態內容」，只印計數已經達到。只在 `--trace` 底下出現、預設不印——那正是沒人跑的報告。

**怎麼驗**：`test-progress-check.sh` 264 → 278（baseline 的可追溯性；已排週次沒被指到：`--check` 仍是 0、摘要有講、`--trace` 列得出來；全部被指到要講；Cancelled 不算；舊格式 `unavailable`＋`None`；沒有〈里程碑〉；`--json` stdout 仍是合法 JSON）。**順帶補上 P0 漏的一條規矩**：P0 加的共用 oracle `run_ms`（現在的 `run_expr`）沒有登記 `selftest_count`——「每個共用 oracle 都要走過一次失敗路徑」是這支測試自己的規矩，這次補登，連同新的 `run_trace_has`。**突變 11 刀**：第一輪存活 1（「`--trace` 不列項目」——`--trace` 也印一般狀態表，那裡本來就有 `APP-P03`，拿 ID 當斷言恆真），明細列加 `↳` 前綴、斷言改抓前綴之後 11/11 紅。GuildHub 真實 WBS：違規數與 P1 版相同，摘要印「未評估（〈里程碑〉是舊的兩欄格式）」。

**過程**：codex（gpt-5.6-sol）＋Gemini（3.1 pro high）第九輪。實作時發現共識裡兩個細節沒談到（差異要不要做、摘要印在哪），兩位都選不做差異、預設印一行。codex 附帶條件：`--json` 不能多這一行。

## 2026-09-25　週次錨點（P3）：純報告；「已裁決」看缺口的狀態，不看阻塞邊的類型

**決定**：`docs/WBS.md` 裡一行 `<!-- wbs:week1 YYYY-MM-DD 時區 -->`（只能一行、**時區寫 IANA 名稱**；不從 git 第一個 commit 推——匯入、rebase、shallow clone 都會讓它無聲失真，人改日期至少 diff 看得見）。W1 是那一天起七天；`決策≤W1` 在 W2 第一天才算過期；錨點之前是 W0。`--as-of YYYY-MM-DD` 把「今天」換掉（測試不准依賴真實時鐘；格式錯或日期不存在就以參數錯誤結束，不默默改用真實時鐘）。
- 有決策期限的缺口三態：**終態（`已完成`＝`Done`，理由寫答案；`已取消`＝`Cancelled`）→ `decided`**；其他（等外部、待裁決、未開始）截止前 `waiting`、截止後 `fallback_effective`（附 `effective_since_week`）。fallback 是強制寫的，期限到了語意上就生效——報告講「fallback 已自 Wn 起生效」，不是永遠叫「未決」。
- **純報告、exit 0**：時間不能進 `--check` 的退出碼（CI 冪等性；無關 PR 會因週末變紅；人會把錨點往後推）。錨點本身的文法錯誤（多行、沒時區、時區認不出來、日期不存在）照樣非零——那是寫錯字，跟時間無關。
- 預設輸出（含 `--check`、不含 `--json`）：有錨點印「今天 Wk；N 個缺口 fallback 已生效」；沒錨點但有決策期限印「未設定」；**完全沒有決策期限的專案什麼都不講**。

**推翻了第二輪 D3**：D3 定「已裁決＝指向缺口的 `待裁決` 類型阻塞邊消失」。開工前量 GuildHub：26 個有決策期限的缺口，指向它們的邊類型是 `待銜接` 43、沒寫 6、`BE-拒` 1——**`待裁決` 0 條**。照 D3，26 個全部「已裁決」，這個機制在唯一的真實 repo 上永遠不出聲（分母為 0，P1 上一次被推翻是同一種形狀）；而且 D3 跟第七輪「用算出來的狀態，不看類型字面」互相矛盾。改看缺口的狀態之後，GuildHub 追 24 個（16 個等外部，多數期限在 W1–W9）——設錨點的第一天可能一次冒出二十幾個，那是終於看見既有積欠，不是新製造的雜訊；細節在 `--trace`。

**拒絕的**：只追 `TBD` 標記的缺口（GuildHub 2 個——16 個期限已過的等外部缺口永遠看不見，正是 P3 要解的「期限全是過去式、每條規則都綠」）；寫死 `Asia/Taipei` 或 UTC（「今天」要依專案所在地解讀，不能把 zh-TW 模板當成所有人都在臺北）；**有決策期限卻沒錨點就讓 `--check` 失敗**（Gemini 第十輪提的）——不變量 4 強制每個缺口都寫 `決策≤Wn`，那條規則等於「每個有缺口的專案都要設錨點否則 CI 紅」，是一道新閘門，GuildHub 當天就紅，而它的 W1 是哪一天是它團隊的規劃事實，agent 不能替它填。

**怎麼驗**：`test-progress-check.sh` 278 → 299。用 `ASOF=…` 釘住今天：錨點起第 6 天是 W1、`waiting`；第 7 天是 W2、`fallback_effective` 自 W2（`--check` 仍是 0）；錨點前是 W0；錨點往後挪七天、同一天的週次少一；Done／Cancelled 是 `decided`；多行錨點、沒時區、時區錯、日期不存在各自紅；圍籬裡的錨點不算；`--as-of` 錯以 2 結束；沒錨點有期限講「未設定」、沒期限不講；`--json` stdout 仍合法。既有的 `run`／`run_expr`／`run_trace_has` 認 `ASOF` 環境變數，沒有新增斷言 oracle。**突變 17 刀全紅**（W1 邊界差一天、期限當週就算過期、Done／Cancelled 不算已裁決、錨點永遠不啟用、多行／格式／時區不驗、圍籬裡的也算、`--as-of` 錯了不停、兩種摘要各自拿掉、沒期限也提示、逾期偷偷變閘門、生效週算錯、摘要混進 `--json`、有 `--as-of` 還用真實時鐘）。GuildHub 真實 WBS：違規數與 P2 版相同，印「週次錨點：未設定——26 個缺口…」；在暫存複本上假設 W1＝2026-08-03 試跑，今天是 W8、20 個缺口 fallback 已生效（GuildHub 真正的 W1 是哪天要它自己定，這裡沒有替它加錨點）。
