# 00 整張地圖（每個專案只跑一次）

我要開始一個**新專案**。請先讀 `AGENTS.md` 與 `CONTEXT.md`。

**現在不要寫任何程式碼，也不要開 change，也不要跑 `01`。**
`01` 是「一個工作項目」的探索；在那之前，先要有整張地圖 ——
不然每個功能都是孤島，串不起來，而且沒有人知道下一步是什麼。

## 先問全貌

逐步問我，一次三到五題，答完再問下一輪。模糊就追問，不要替我補完。
問法要**具體到能答對或答錯**：「安全要做好」不是答案，「登入失敗三次之後會怎樣」才是。

1. **這個產品讓誰達成什麼結果** —— 一句話一個角色。列不出角色就還沒到可以規劃的時候。
2. **端到端的主要流程有哪幾條** —— 從進來到拿到結果，每一條走過哪幾步。
3. **外部系統與依賴** —— 後端、第三方、別的團隊。每一個：現在有沒有、誰負責、
   沒有的話最晚什麼時候要有。
4. **資料的所有權** —— 哪些資料是這個系統的、哪些只是引用別人的。
5. **明確不做的事** —— 寫下來的「不做」跟「沒想到」是兩件事。
6. **難逆轉的取捨** —— 有沒有第一天就非決定不可的邊界（例如：一定要離線可用、
   一定不能自己存個資）。**有就開一份 ADR（Status: Proposed）**，照
   `docs/adr/_template.md`；沒有就不要硬湊。
7. **最大的未知** —— 哪幾件事現在答不出來、什麼時候一定要有答案、沒答案的話先怎麼辦。

最後一定要問一次：**剛才講定的東西，有哪些還沒寫進任何檔案？**
穩定下來的詞彙進 `CONTEXT.md`。

## 再攤成 `docs/WBS.md`

把上面問出來的東西攤成一張工作分解表。**這張表是地圖，不是架構圖** ——
它寫「要交付什麼、什麼順序、誰擋著誰」，不寫「系統怎麼切」。

**粗細：全局覆蓋、近期細化。**

- 全產品：每一條使用者結果、營運上必要的工作、每一個外部依賴、明確不做的事，都要有一列。
- **下一個里程碑**拆到「可以開一份 spec PR」的程度：每項有可觀察的完成結果、依賴、順序。
- 再下一個里程碑拆到看得出主要依賴與風險。
- 更後面的只留結果型的一列，點數寫 `—`。**不要第一天估滿點數、不要拆到幾百列** ——
  那是假精確，衍生專案三個月後才長到 251 列。

**停止拆分的判準不是列數**，是同時滿足：知道下一個可以開的 change 是哪個；
知道它需要哪些既有能力或外部裁決；主要流程沒有整段消失；
**沒有假裝知道內部模組將怎麼切。**

**分組**：先以使用者結果、端到端流程或交付里程碑分組；跨多個流程的基礎工作可以用
工程工作群（「即時同步」「身分與存取」）。分組標題與每一列的「工作」欄**寫可觀察的
交付結果、風險裁決或外部合約**，不寫 store、container、adapter、layer 這種內部切法，
也不寫「未來會有哪些 capability」——那些會被 change 修正，寫進地圖只會讓地圖過期。
衍生專案的反證：地圖上寫「資料層」一項，實作時拆成兩個 capability，是對的，
而地圖不用改 —— 因為它寫的是交付結果，不是切法。

格式（**七欄，前五欄必填**；文法在 `AGENTS.md`〈改 `docs/WBS.md` 之前〉，
`progress.sh --check` 會驗，打錯一個字元會紅，那是刻意的）：

```markdown
## 阻塞類型

| 阻塞類型 | 意思 | 該做什麼 |
|---|---|---|
| `待銜接` | 本地先做了，之後要對齊 | 照常排週次 |
| `待裁決` | 語意還沒定 | 人要拍板，寫決策期限 |

| APP-C01 | 進入 | 打開就看得到自己的東西，沒登入會被帶去登入 | W1 | 3 | | |

| ID | 項目 | 工作 | 週 | 點 | 阻塞 | 標記 |

| DEP-G01 | 對方有沒有搜尋 | 去問。**【沒答案就】**介面叫「瀏覽」，不叫搜尋 | 決策≤W1 | — | `待裁決` | Alarm｜核心價值 |

## 里程碑

| 里程碑 | 意思 | 靠哪些 |
|---|---|---|
| M1 一個人跑完主流程 | 進來、看到、做完一件事 | APP-C01、APP-C02 |

<!-- progress:start 這一段由 `progress.sh --render` 產生，不要手改 -->

```

每個里程碑用 ID 指向支撐它的工作，重排之後懸空的引用機器會抓。
外部依賴「還沒有」不是牆：照樣排週次，週次就是對方最晚要交的時間；
「對方明文不做」才是牆，要收斂成刪需求／自己降級／重新裁決三者之一
（規則在 `AGENTS.md`〈開 change 之前先看它擋在哪〉）。

寫完跑：

```bash
bash .github/scripts/progress.sh --check    # 文法、引用、缺口的期限與 fallback
bash .github/scripts/progress.sh --all      # 整張地圖，還沒開始的也列
```

**地圖用 `governance/` 分支進 main**（`docs/WBS.md` 只有它能動）。
進了 main 之後，才開第一個 change：`01` → `02`。

## 地圖之後會被 change 修正 —— 那是正常的

地圖寫的是交付意圖。change 在規格階段發現要拆、要合、要換順序，**是規格對，
不是地圖錯** —— 但地圖要跟上：

- capability 內部拆分、而交付結果／順序／阻塞沒變 → **不改地圖**。
- 交付結果、順序、依賴、範圍改了，或地圖的文字仍宣稱一個已被推翻的邊界 →
  **由該 change 的提案者開最小的 `governance/` PR 改地圖**，在 `/opsx:apply` 之前合併。
- 要開的 change 在地圖上找不到 ID → 先改地圖，**不要現場發明一個 id**：
  `progress.sh --check` 會把對不上任何 WBS ID 的 change 判成違規，
  `spec/` 的 PR 在規格階段就會紅。地圖先於 change。

---

**跟 superpowers 的關係**：`brainstorming` 可以拿來輔助上面的訪談，
`writing-plans` 可以拿來想一個工作項目怎麼實作 —— 它們是**功能層**的工具，
輸出不是 source of truth。專案層的地圖是這份 WBS，規格是 OpenSpec，
邊界是 ADR。用 plan 當總體計畫，得到的是一疊互不相連的 plan ——
那正是這一步要防的事。
